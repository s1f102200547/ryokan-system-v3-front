# Local Development 仕様（Firebase Emulator）

## 1. 目的

- ローカル開発から本番の Firestore / Auth に **到達できる経路をなくす**。
- 開発者の PC に **本番の認証情報を常駐させない**。PC 内のファイルを不正に見られても、本番の環境とデータには届かない状態にする。
- 開発用データは **本番と同じ形**（キーの欠損、型違い、`''` と `null` の混在、壊れた値）を持ち、**個人を特定できない** ものにする。

## 2. 用語

| 用語 | 意味 |
|---|---|
| Emulator | Firebase Emulator Suite（Firestore + Auth） |
| demo project | `demo-` で始まる project ID（例: `demo-ryokan`）。Emulator 専用で、本番リソースに届かない。Firebase コンソールでの作成は不要 |
| 匿名化データ | 本番から機械的に生成した、元に戻せない開発用データ |
| 形 | フィールドの有無、型、`''` / `null` の区別、破損値。値の中身は含まない |
| 閲覧専用 SA | `roles/datastore.viewer` のみを持つ、匿名化専用のサービスアカウント |

## 3. 全体の流れ

```
本番 Firestore ──(閲覧専用SA, 読み取りのみ)──> 匿名化 ──(メモリ上で変換)──> 匿名化データ（ローカル）
                                                                              │
Emulator (demo project) <──────────── 投入（日付を今日に合わせる）─────────────┘
       ↑
  開発サーバー
```

## 4. 要件

### 4.1 開発サーバーの接続先（DEV）

| ID | 要件 |
|---|---|
| DEV-1 | 開発サーバーは Emulator（Firestore + Auth）にだけ接続する |
| DEV-2 | サーバー側は、development のとき次をすべて満たさなければ **起動を拒否** する<br>・Firestore Emulator の接続先が設定されている<br>・Auth Emulator の接続先が設定されている<br>・project ID が `demo-` で始まる |
| DEV-3 | Emulator 接続時のサーバー側は、認証情報を渡さずに初期化する。ADC（Application Default Credentials）への fallback も起きないようにする |
| DEV-4 | ブラウザ側の Auth も Auth Emulator に接続する（サーバーとブラウザで接続先を揃えないと、トークンの検証が失敗する）。接続処理は1か所に集約し、Auth を使う箇所はすべてそこを経由する |
| DEV-5 | CSP の `connect-src` には **development のときだけ** Auth Emulator のアドレスを加える。production の CSP は変えない |
| DEV-6 | 開発用の環境設定に本番の鍵を置かない |

### 4.2 匿名化（ANON）

#### 実行条件

| ID | 要件 |
|---|---|
| ANON-1 | 本番の読み取りは閲覧専用 SA の権限を借りて行う。鍵ファイルは作らない |
| ANON-2 | ログインは匿名化の実行時だけ行い、終了時（エラー終了・中断を含む）に PC 上の認証情報を必ず削除する。認証情報が PC にあるのは実行中だけで、その間も権限は閲覧専用である |
| ANON-3 | Emulator の接続先が設定された環境では実行を拒否する（Emulator を本番と取り違えないため） |
| ANON-4 | 本番に対しては読み取りだけを行う |
| ANON-5 | 変換はメモリ上で行い、**ディスクに書くのは匿名化後のデータだけ** にする。生データの一時ファイルも作らない |
| ANON-6 | 匿名化データはリポジトリにコミットしない（各自のローカルで生成し、Git の管理対象外に置く）。コミットするのは生成手段だけにし、いつでも作り直せるようにする |

#### 変換規則

**許可リスト方式** とする。下表で「残す」と明示したフィールド以外は、未知のフィールドも含めてすべてマスクする。`gmail-listener` が新しいフィールドを追加しても、個人情報が素通りしない。

| 対象 | 扱い |
|---|---|
| 業務ロジックに必要な値（部屋、人数、時刻、`cancel`, `late_out`, `booking_site`, `room_type`, `stay_plan`, `total_price` など） | そのまま残す |
| 日付（`check_in_date`, `check_out_date`, `dailyInfo` の日付） | 実行ごとに決める乱数の日数でずらす。乱数は保存しない。同じ実行内では全レコードで同じ日数を使い、泊数・連泊の関係を保つ |
| 破損した日付（例: `2026-13-99`） | **ずらさずにそのまま残す**。正規化すると実在の日付に変わり、破損が消える |
| `country` | レコード間でシャッフルする（分布は残し、個人との対応を切る） |
| `city` | マスクする |
| `mail_memo` | `summary`, `source`, `month`, `day` は残し、`name`, `text` などそれ以外はマスクする |
| ドキュメント ID、`reservation_number`、todo の `id` | 乱数で振り直す。同じ実行内では、同じ元の値は同じ新しい値に対応させる（参照関係を保つ） |
| Timestamp など Firestore 固有の型 | 型を保ったまま受け渡す |
| 上記以外（`guest_name`, `remarks`, `timetable_info`, `dinner_info`, スタッフ名、未知のフィールド） | 下の「マスク」を適用する |

#### マスク

| 元の値 | マスク後 |
|---|---|
| 文字列 | 文字数と、文字ごとの種類（数字、英字、ひらがな、カタカナ、漢字、その他）を保ったまま乱数の文字に置き換える。空白・改行・記号はそのまま残す（印刷レイアウトの確認に必要） |
| 数値 | 同じ桁数の乱数（整数か小数かも保つ） |
| `''`, `null`, 真偽値 | そのまま |
| 配列、マップ | 要素ごとに再帰的に適用する |

- ハッシュは辞書攻撃で戻せるため使わない。
- 匿名化後も、日付・部屋・人数・国の組み合わせから個人を推定できる可能性は残る。匿名化データは開発者のローカル以外に渡さない。

#### 出力

| ID | 要件 |
|---|---|
| ANON-7 | 匿名化データには **匿名化した日** を記録する |
| ANON-8 | 実行のたびに **形のレポート** を出力する。内容はコレクション・フィールドごとの型の件数（`string` / `number` / `null` / `''` / 欠損 / 破損日付 など）だけで、値は含めない |
| ANON-9 | 前回のレポートと比べて型の種類が増えたフィールドを警告する（本番データの形が変わった合図） |

### 4.3 Emulator への投入（SEED）

| ID | 要件 |
|---|---|
| SEED-1 | Firestore / Auth Emulator の接続先が設定され、かつ project ID が `demo-` で始まる場合だけ実行する。満たさなければ何もせず終了する |
| SEED-2 | 投入前に Emulator の全データと全ユーザーを削除する |
| SEED-3 | 日付を **「今日 − 匿名化した日」** だけずらして投入する。アプリの表示範囲（今日から過去100日〜未来365日）にデータが収まり続ける。破損した日付はずらさない |
| SEED-4 | Emulator 専用の開発用ログインユーザーを作る |

### 4.4 運用（OPS）

| ID | 要件 |
|---|---|
| OPS-1 | 匿名化データは月1回程度、およびリリース前に作り直す |
| OPS-2 | 本番の書き込み権限を持つ鍵で、開発用途に使っていたものは無効化する。PC に本番の鍵を置かない |
| OPS-3 | PC から本番へデプロイするときは、その都度ログインし、終わったらログアウトする。PC からデプロイしない場合は、ログアウトした状態を保つ |
| OPS-4 | 普段の PC には、gcloud・Firebase CLI のどちらにも本番の認証情報が残っていない |

## 5. 受け入れ基準

- [ ] Emulator の接続先を外すと、開発サーバーの起動が拒否される
- [ ] project ID を `demo-` 以外にすると、開発サーバーの起動が拒否される
- [ ] ADC がログイン済みの PC でも、上の2つで本番に接続しない
- [ ] 開発用ユーザーでログインでき、予約一覧に匿名化データが表示される
- [ ] 画面での保存・キャンセル・追加が Emulator にだけ反映される
- [ ] Emulator の接続先が設定された環境で、匿名化が拒否される
- [ ] Emulator の接続先がない環境で、投入が拒否される
- [ ] 匿名化の終了後（中断・エラー時を含む）、PC に本番の認証情報が残っていない
- [ ] 普段の PC で、gcloud・Firebase CLI のどちらにも本番の認証情報がない
- [ ] 許可リストにないフィールドを含むテストデータを匿名化すると、そのフィールドがマスクされる
- [ ] 破損した日付が、匿名化と投入の後も同じ値のまま残る
- [ ] 匿名化データが Git の管理対象に現れない
- [ ] production の CSP に Emulator のアドレスが含まれない
- [ ] E2E が通る

## 6. 発展

- 匿名化データ全件をデータ読み込み処理（Infra 層のパーサー）に通すテストを置き、「実際のデータの形」を判定基準にする（`docs/BugHunting.md`）。
