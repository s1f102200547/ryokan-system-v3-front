# Bug Hunting Strategy

テストの目的を「品質の保証」ではなく「バグの発見」と「発見済みバグの再発防止」に置く。

基本サイクル:

```
リスクの高い場所を選ぶ → 仕様に依存しない判定基準で探す → 直す → 回帰テストにする → 同じ原因を横展開で探す
```

---

## 1. 前提: なぜ今のテストではバグが見つからないか

### 1.1 期待値が「なぞり」になる

仕様 md もコードも AI と一緒に書いているため、期待値を md から取ってもコードから取っても **同じ解釈をなぞるだけ** になる。md の穴や誤解はそのままコードとテストに写り、テストはすべて通る。過去のバグの多くはテストではなく、人が実際にアプリを使って見つけている（「未定と表示されない」「大人 0 人で保存失敗」「最終夜に清掃ボードの人数が出ない」「保存前にモーダルを閉じると消える」など）。

### 1.2 テストの盲点（層ごと）

| テスト | モックしているもの | 構造的に検出できないバグ |
|---|---|---|
| `tests/unit/` | なし（Domain の純粋関数のみ） | Infra の `toReservation`、Application の集計、`dateUtils` の TZ 依存 |
| `tests/integration/` | Application 層と `verifySession` を丸ごと `vi.mock` | Route の Zod と Infra の Zod の食い違い、Firestore のエラーコードの分類、読み戻し時の破損 |
| `e2e/` | API を `page.route` で丸ごと mock | Route Handler 以降のすべて。mock の JSON が実際の API と食い違っても通る |

つまり **「Route が受け付けた値を Firestore に書き、読み戻して画面に出す」という一番バグが多い経路を、どのテストも通していない**。git 履歴で最も多かったバグ（`adult_count` の下限、`room` の null、`''` と `null`、日付の書式）はすべてこの経路で起きている。

### 1.3 判定基準を md やコードの外に置く

| 判定の基準（オラクル） | 手法 |
|---|---|
| 「受け付けたものは、読み戻せる・消えない・他を壊さない」 | §3.1 往復検査 |
| 「同じ制約はどこでも同じ」 | §3.2 制約の突き合わせ（横展開） |
| 「入力が原因で 5xx を返さない・ALERT を鳴らさない」 | §3.3 ファジング |
| 「どの TZ・どの時刻に動かしても同じ答え」 | §3.4 時刻・TZ の固定テスト |
| 単純な不変ルール | §3.5 PBT |
| 実際に動いているアプリ、ユーザーの常識 | §3.6 実機確認と探索的テスト |
| 操作の順序が変わっても壊れない | §3.7 状態遷移と競合 |

仕様そのものの誤り（作るべきものが違う）はどの手法でも見つからない。自分で使うことと、現場のスタッフに触ってもらうことで補う。

## 2. リスクマップ: このプロジェクトでバグが出やすい場所

コードを読んで洗い出した、バグの温床になっている構造。探索はここから優先して行う。

### R1. 同じ制約が5か所に分かれて書かれている

予約の1フィールドの制約が、次の5か所に別々に書かれている。1か所だけ直すと残りが食い違う。

| 場所 | 例 |
|---|---|
| UI の選択肢 | `src/constants/guestInfo.ts` の `arrivalOptions` など |
| Route の Zod | `src/app/api/reservations/[id]/route.ts` の `PatchBodySchema` |
| TS 型 | `src/types/guestInfo.ts` の `ReservationPatch` |
| Infra の Zod と許容値 | `src/infra/reservation/firestoreReservationRepository.ts` の `FirestoreReservationSchema`、`*_VALUES` |
| DB の実データ | Gmail 取り込み（別システム）が書いた値 |

特に Route の `PatchBodySchema` は `dinner_time`・`breakfast_time`・`open_air_bath_time`・`arrival_time` を **任意の文字列** で受け付け、配列の長さも見ない。一方 Infra は読み取り時に許容値以外を fallback に置き換え、長さが泊数と違えば配列全体を初期化する。

### R2. 読み取り時の正規化が、書き込みの失敗を隠す

`toReservation` は不正値を黙って fallback に置き換え、破損ドキュメントは `console.error` だけでスキップする（ALERT なし）。そのため「保存は成功したのに、読み戻すと値が消えている」「予約が画面から黙って消える」が、エラーとして表に出ない。予約が消えると、空室に見えてダブルブッキングにつながる。

### R3. 日付と時刻の扱いが3系統ある

- 書式: Firestore は `YYYY/MM/DD`、API 内部は `YYYY-MM-DD`、`dailyInfo` の ID は `YYYY-MM-DD`。
- 時刻の基準: JST を明示的に計算する箇所（`getTodayJST`, `proxy.ts`, `msUntilToday23JST`）と、**実行環境のローカル時刻** に依存する箇所（`addDays`、`isRealDate`、`addReservationCommand` の `getMonth()/getDate()`、`computeProcessedRows` の `toISOString()` と `new Date(str)`）が混在する。Cloud Run は UTC、ブラウザは JST、CI は UTC。
- 窓: UseCase は「対象日の前後 30 日」の check_in で予約を取るため、31 泊以上の滞在は見えない。

JST 0:00〜9:00 は UTC では前日なので、本番の営業時間（6:00〜23:00 JST）のうち **6:00〜9:00 が日付ずれの危険時間帯** になる。

### R4. 泊数に連動する配列

`dinner_time` などの泊別配列は泊数と、`age_groups` は `adult_count` と同じ長さでなければならない。長さを揃えるのは UI（`ReservationModal.tsx` の `handleFieldChange`）だけで、Route も Infra の書き込みも検査しない。泊数が 0 以下になると、読み取り時の `Array(nights)` が `RangeError` を投げる。

### R5. Firestore のエラー分類が「その他はすべて障害」

`withFirestoreError` は gRPC code 14 と 7 以外をすべて `FIRESTORE_UNAVAILABLE`（503 + Slack ALERT）にする。存在しない ID への `update()`（NOT_FOUND = 5）や、不正なドキュメントパスなど **入力が原因の失敗** も障害として通知される。`[id]` パラメータは Zod で検証していない。

### R6. 自動保存と書き込みの競合

モーダルは 500ms debounce の自動保存で、配列フィールドは **配列ごと上書き** する。トランザクションはない（`docs/KnownIssues.md`）。2 タブや 2 人で同じ予約を開くと、後から保存した側が前の変更を消す。過去にも「保存中にモーダルを閉じる」レースがあった。

### R7. 部屋状態の計算は「1部屋に有効な予約は1件」が前提

`computeRoomCheckInState` は `find` で最初の1件だけを使う。同じ部屋・同じ夜に2件あると、2件目は清掃ボードにもタイムテーブルにも出ない。ダブルブッキングの検査はどこにもない。

### R8. 時間で変わる挙動

本番のみの時間帯制限（6:00〜23:00）、セッション期限（当日 23:00、最低 5 分）、`DATE_RANGE_*` の範囲チェックは、すべて実行時刻で結果が変わる。`proxy.ts` の matcher は `/api` を除くため、API には時間帯制限がかからない（0:00〜6:00 JST にログイン API を直接呼ぶと、その日の 23:00 まで、最大で約 23 時間有効な Cookie が発行される）。

## 3. 手法

### 3.1 往復検査（最優先）

**課題**: §1.2 のとおり、Route → Infra → 読み戻しの経路をどのテストも通していない。R1・R2・R4 のバグはここに集中する。

**解決策**:

- `toReservation` と書き込み用の変換を Infra から export し（または Firestore Emulator に対して実際に書いて読み）、次を検査する。
  - Route の Zod が **受け付けた** patch を書いて読み戻すと、patch の値がそのまま返る（fallback に化けない）。
  - どんな patch を書いても、そのドキュメントを含む範囲の `fetchByDateRange` が throw しない。
  - 1件の破損ドキュメントが、他の予約の取得を巻き込まない。
- 判定は仕様の中身に依存しない。「受け付けたのに消えた」「1件のせいで全体が落ちた」はどちらも、仕様がどうであれバグ（入口で拒否すべき）。
- Emulator で行う場合は `make` で立ち上げた環境と人工データ（`docs/LocalDevelopment.md` §8）を使う。

### 3.2 制約の突き合わせ（横展開）

**課題**: 1つのバグを直しても、同じ原因のバグが別の場所に残る（R1）。例: `POST /api/reservations` には `check_out_date > check_in_date` の refine があるが、`PATCH /api/reservations/[id]` にはない。

**解決策**:

- 予約と日次データの全フィールドについて、R1 の5か所の制約を1枚の表に並べ、食い違いを洗い出す。表は md ではなくテストとして持つ（例: UI の選択肢の値がすべて Route の Zod を通り、かつ Infra の許容値に含まれることを検査する）。
- バグを直したら、**原因のパターン** を言語化して全 Route・全 Infra を grep する。このプロジェクトで既に見つかっているパターン:
  - 入口の Zod に refine がない（日付の前後、実在日、範囲）
  - `request.json()` を catch していない
  - 実行環境のローカル時刻に依存している
  - 外部エラーを「その他はすべて障害」に分類している
- 根本対策は、同じ制約を1か所のスキーマに集約し、UI の選択肢・Route・Infra がそれを参照する形にすること。

### 3.3 ファジング

**課題**: テストは「まともな入力」しか試さないため、変な入力で壊れる箇所が残る。

**解決策**:

- 全 Route Handler に対して、body・query・**path params** に次を送るテストを書く。
  - body: 不正な JSON、空、`null`、配列、型違い、巨大な文字列・配列、負の数、小数、`NaN` 相当
  - 日付: `2026-02-30`、`2026-13-01`、`0000-00-00`、範囲外、逆転、同日
  - `[id]`: 存在しない ID、空、`/` や `%2F` を含む、`..`、1500 バイト超（Firestore の ID 上限）
- 判定の規則: **「入力が原因で 5xx を返さない、Slack ALERT を鳴らさない」**。インフラ障害の 503 は正しい挙動なので、Infra を mock する版（入力検証の網羅）と、Emulator に向ける版（R5 のエラー分類の検証。存在しない ID は 404 になるべき）の2本立てにする。
- 書き込み API は mock か Emulator 上で実行する。

### 3.4 時刻・タイムゾーンの固定テスト

**課題**: R3・R8 のバグは、開発者の PC（JST）でも CI（UTC）でも、テストを書いた時刻によっては通ってしまう。

**解決策**:

- `dateUtils`・`dateSchema`・Application の UseCase・`computeProcessedRows` のテストを、`TZ=UTC`、`TZ=Asia/Tokyo`、`TZ=America/Los_Angeles` の3通りで実行する（Vitest の project を分けるか、CI の matrix にする）。判定は「TZ によって結果が変わらない」。
- `vi.useFakeTimers()` で時刻を固定し、境界の時刻を必ず通す: JST 5:59 / 6:00 / 8:59 / 9:00 / 22:54 / 22:56 / 23:00 / 0:00。
- 日付の境界: 月末、年末年始、閏年の 2/29、`DATE_RANGE_PAST_DAYS` と `DATE_RANGE_FUTURE_DAYS` のちょうど端と1日外。

### 3.5 PBT（Property-Based Testing）

**課題**: 具体的な期待値を書くテストは、書いた人の想定した入力しか試さない。AI にコードから性質を考えさせると、バグに合わせた性質になる。

**解決策**:

- md から **単純で一般的な性質** を立て、fast-check で大量の入力を試す。このプロジェクトの候補:
  - `dateDiff(a, addDays(a, n)) === n`（任意の TZ で）
  - `toReservation` の結果の泊別配列の長さは常に泊数と、`age_groups` の長さは `adult_count` と一致する。入力がどんな値でも throw するのは `FIRESTORE_DATA_CORRUPTION` だけ
  - `resizeNightFields` で伸ばして縮めると元に戻る（縮めた分を除く）
  - `computeRoomCheckInState`: 対象日に滞在中の予約があれば `isTodayVacant` は false。CI 日と CO 日は同じ日に `staying` にならない
  - 宿泊税の合計は、行ごとの税の和と一致する。キャンセル済みは含まない
  - 同じ部屋・同じ夜に有効な予約は2件以上存在しない（R7）
- 失敗したら「実装のバグか、性質の立て方の誤りか」を md を根拠に判定する。**md に根拠が見つからなければ仕様の穴** として人間が判断する。
- 報告の半分近くが誤報になりうるため、最終確認は人間が行う。

### 3.6 実機確認と探索的テスト

**課題**: 単体テストや mock を使ったテストは「テストは通るのにアプリは動かない」状態を見逃す。また、テストは誰も想定していなかった使い方を試さない。

- 実例 (2026-10-31): `.env.development` のキー名が `NEXT_PUBLIC_FIREBASE_PRIVATE_KEY` で、`admin.ts` が読む `FIREBASE_PRIVATE_KEY` と一致せず、ログイン API が 503 を返していた。テストは `verifySession` を mock しているため、すべて通っていた。

**解決策**:

- env、認証、DB、SSR、CSP など **境界に触れる変更** では、Emulator 環境でアプリを起動して変更箇所を実際に操作し、証拠（画面、HTTP レスポンス、ログ）を残す。Claude Code では `run` スキルを使う。
- AI エージェントにブラウザ（Playwright MCP）で触らせる探索的テストは、チャーター（狙い）を決めて行う。判定基準は「ユーザーならこう動くと期待する」という常識。チャーターの例:
  - C/O 日を DatePicker にキーボードで直接入力し、C/I 日以前・同日・遠い未来にする。その後、前後の日のダッシュボードが表示できるか
  - 泊数を伸ばす・縮めると、夕食・朝食・露天の入力がどうなるか。保存後に再読み込みしても残っているか
  - 大人の人数を 0 や 9 にして、年代の入力がどうなるか
  - 同じ予約を2タブで開いて別々に編集する。保存中にモーダルを閉じる、ネットワークを切る
  - キャンセル → 復活 → キャンセルを繰り返す。キャンセル済みの予約を編集する
  - 月をまたぐ連泊、31 泊以上の予約を宿泊税テーブル・清掃ボード・タイムテーブルで見る
  - 部屋未定の予約、同じ部屋・同じ日に2件ある予約を清掃ボードで見る
  - 宿泊税テーブルを月初・月末・JST 6:00〜9:00 に開く
  - 印刷プレビューで情報が欠けないか（長いゲスト名、7部屋すべて埋まった日）
- 報告されたバグは再現を確認してから直し、回帰テストにする。
- 前提: **本番の Firestore に対して操作させない。** Emulator と人工データ（`make`、`docs/LocalDevelopment.md` §8）を使う。予約データにはゲストの個人情報が含まれるため、実データは使わない。

### 3.7 状態遷移と競合

**課題**: R6 のバグは、1回ずつの操作では再現しない。過去にも保存とモーダルを閉じる操作のレースがあった。

**解決策**:

- 予約の状態（通常 / キャンセル済み）と操作（編集・キャンセル・復活・宿泊税チェック）の組み合わせを表にし、「同じ操作を2回」「キャンセル済みに編集」「存在しない ID に操作」を一通り試す。
- 自動保存は hooks のテストで、debounce 中の close、保存失敗後の再編集、レスポンスの到着順の逆転を再現する。
- 同時編集は仕様判断（楽観ロックを入れるか）とセットで扱う。

### 3.8 本番の観測

**課題**: 本番のユーザー操作は最強のバグ発見手段だが、今は不正な入力でも Slack [ALERT] が鳴るため、本物の障害がノイズに埋もれる。逆に、破損ドキュメントのスキップ（R2）は何も通知されない。

**解決策**:

- 入力起因のエラーは 4xx にして ALERT を鳴らさず、ALERT は「人が対応しないと直らない障害」に限定する（`docs/ErrorHandling.md` の方針どおり）。
- 破損ドキュメントのスキップは `logger` で WARN 以上を出し、件数を観測できるようにする。Gmail 取り込み側のバグの検出にも使える。
- ログイン失敗の WARN ログは、ブルートフォース検知（`docs/KnownIssues.md`）にも使う。

## 4. 発見したバグの再発防止

探索的な手法は毎回結果が変わり、AI が高速にコードを書き換える開発では再発のリスクが高い。

- 見つけたバグは、直すときに必ず **最小の再現ケースを回帰テストとして追加** する。

| バグの場所 | 回帰テストの置き場 |
|---|---|
| Domain、純粋関数 | `tests/unit/` |
| Infra の変換（`toReservation` など） | `tests/unit/`（export して純粋関数として） |
| Route Handler の入力検証・status | `tests/integration/` |
| 画面操作 | `e2e/` |

- 回帰テストの役割は仕様の正しさの保証ではなく、**直したバグを戻さないこと** と割り切る。
- 直したら §3.2 の横展開を必ず行い、下の表に原因のパターンを残す。

## 6. 進め方

ステップごとの手順・完了条件・進捗は `docs/BugHuntingRunbook.md` にまとめている。

1. **#4 を Emulator で再現する**。再現したら #3・#4・#6・#7 をまとめて直す（入口の Zod を Infra の許容値に揃える + 読み取りで泊数 0 以下を `FIRESTORE_DATA_CORRUPTION` にする）。それぞれ回帰テストにする。
2. #1・#2・#5 を直す（入力起因は 4xx、ALERT を鳴らさない）。
3. §3.1 の往復検査と §3.2 の制約の突き合わせテストを追加する。ここが今のテストの最大の穴。
4. §3.3 のファジングを全 Route Handler に共通で追加する。
5. §3.4 の TZ・時刻の固定テストを追加し、#8・#9 を確認して直す。

7. §3.5 PBT、§3.6 探索的テスト、§3.7 競合に進む。前提の Emulator と人工データは用意済み（`make`。`docs/LocalDevelopment.md` §8）。
8. 境界に触れる変更では、常に実機で確かめる（§3.6）。
