# Bug Hunting

テストの目的を「品質の保証」ではなく「バグの発見」と「発見済みバグの再発防止」に置く。

```
リスクの高い場所を選ぶ → 仕様に依存しない判定基準で探す → 直す → 回帰テストにする → 同じ原因を横展開で探す
```

2026-10-31 にこの方針で一巡し、28 件の課題を洗い出して対応を終えた（§5）。仕様として決めたことは §6、残っていることは §7 にある。以後は、機能を追加・変更するときに §3 の手法と §4 の横展開を使う。

---

## 1. 考え方

### 1.1 期待値が「なぞり」になる

仕様 md もコードも AI と一緒に書いているため、期待値を md から取ってもコードから取っても **同じ解釈をなぞるだけ** になる。md の穴や誤解はそのままコードとテストに写り、テストはすべて通る。過去のバグの多くはテストではなく、人が実際にアプリを使って見つけていた（「未定と表示されない」「大人 0 人で保存失敗」「最終夜に清掃ボードの人数が出ない」「保存前にモーダルを閉じると消える」など）。

### 1.2 テストの盲点（層ごと）

| テスト | モックしているもの | 構造的に検出できないバグ | 今は何で補っているか |
|---|---|---|---|
| `tests/unit/` | なし（純粋関数） | Infra の変換、Application の集計、TZ 依存 | `toReservation` を export して unit で、TZ は `tests/time/` |
| `tests/integration/` | Application 層と `verifySession` | Route と Infra の制約の食い違い、Firestore のエラーの分類、読み戻し時の破損 | `tests/emulator/`（往復検査）と `tests/unit/constraints/` |
| `e2e/` | API を `page.route` で丸ごと | Route Handler 以降のすべて | `tests/emulator/` と、Emulator での実機確認 |

一番バグが多かったのは **「Route が受け付けた値を Firestore に書き、読み戻して画面に出す」経路** で、以前はどのテストも通していなかった。今は `tests/emulator/` が実際の Firestore Emulator に書いて読む。

### 1.3 判定基準を md やコードの外に置く

| 判定の基準（オラクル） | 手法 |
|---|---|
| 「受け付けたものは、読み戻せる・消えない・他を壊さない」 | §3.1 往復検査 |
| 「同じ制約はどこでも同じ」 | §3.2 制約の突き合わせ（横展開） |
| 「入力が原因で 5xx を返さない・ALERT を鳴らさない」 | §3.3 ファジング |
| 「どの TZ・どの時刻に動かしても同じ答え」 | §3.4 時刻・TZ の固定テスト |
| 単純な不変ルール | §3.5 PBT |
| 実際に動いているアプリ、ユーザーの常識 | §3.6 実機確認と探索的テスト |
| 操作の順序や回数が変わっても壊れない | §3.7 状態遷移と競合 |

仕様そのものの誤り（作るべきものが違う）はどの手法でも見つからない。自分で使うことと、現場のスタッフに触ってもらうことで補う。

## 3. 手法と、今あるテスト

すべて `make check`（ローカル）と CI で毎回実行される。`make` で起動した開発用の Emulator・開発サーバーは止めてから `make check` を実行する（E2E が起動中のサーバーを再利用し、Emulator 系のテストはポートが衝突するため）。

| 手法 | テスト | 実行 |
|---|---|---|
| §3.1 往復検査 | `tests/emulator/reservationRoundTrip.test.ts` | `npm run test:emulator` |
| §3.2 制約の突き合わせ | `tests/unit/constraints/` | `npm run test` |
| §3.3 ファジング | `tests/integration/fuzz/`（mock 版）、`tests/emulator/routes.fuzz.test.ts`（Emulator 版） | `npm run test`、`npm run test:emulator` |
| §3.4 時刻・TZ | `tests/time/` | `npm run test:tz`（UTC / Asia/Tokyo / America/Los_Angeles） |
| §3.5 PBT | `tests/pbt/`、`tests/time/dateProperties.test.ts` | `npm run test`、`npm run test:tz` |
| §3.7 状態遷移と競合 | `tests/emulator/stateTransitions.test.ts`、`e2e/guestInfo.spec.ts` の「保存の失敗」「保存の順序」 | `npm run test:emulator`、`npm run e2e` |

### 3.1 往復検査

Route Handler → Command → Infra → Firestore Emulator に実際に書き、画面と同じ読み取り経路で読み戻す。モックは認証と Slack だけ。

- 判定: Route が受け付けた値は読み戻しても同じ（fallback に化けない）。壊れたドキュメントが1件あっても他の予約の取得を巻き込まない。どちらも仕様の中身に依存しない。
- 対象: 許容値のある全フィールドの全値、自由入力の境界（上限の文字数・空・記号・改行・絵文字）、泊数の変更、壊れたドキュメント 12 種。

### 3.2 制約の突き合わせ（横展開）

UI の選択肢（UI が送る形）→ Route の Zod → Infra の読み取り、の3か所で値が消えないことを検査する。UI の選択肢をテストが直接参照するので、選択肢を足すと自動で検査対象になる。

- バグを直したら、**原因のパターン** を言語化して全 Route・全 Infra・全 UseCase を grep する（§4 の一覧）。
- 根本対策は、同じ制約を1か所に集め、各層がそれを参照する形にすること。

### 3.3 ファジング

全 Route Handler に、壊れた body・path・query を送る。入力の一覧は `tests/utils/fuzzInputs.ts`。

- 判定: **入力が原因で 5xx を返さない・Slack に通知しない**。
- mock 版は Application / Infra を mock して入力検証を網羅し、`src/app/api/**/route.ts` を走査して対象の漏れも検査する（Route を追加したら、対象に足さないとテストが落ちる）。
- Emulator 版は実際の Firestore / Auth に向けて、エラーの分類まで確かめる。
- 分かったこと: 空白・NUL 文字・`%2F` という文字列は Firestore のドキュメント ID として有効。入口で拒否せず、存在しなければ 404 を返す。

### 3.4 時刻・TZ の固定テスト

- `tests/time/` を3つの TZ で実行し、判定は「TZ によって結果が変わらない」。
- 時刻は `tests/utils/timeHelper.ts` の `setNowJST` で JST の日時として固定し、境界（0:00 / 5:59 / 6:00 / 8:59 / 9:00 / 22:54 / 22:56 / 23:00 / 23:59）を通す。日付は月末・年末年始・閏日・米国の夏時間の切り替え日、`DATE_RANGE_*` の端と1日外。
- 期待値は具体的な値で書く。スナップショットは最初に実行した TZ の値を固定してしまうので使わない。

### 3.5 PBT（Property-Based Testing）

fast-check で大量の入力を生成し、単純で一般的な性質を確かめる。入力の生成器は `tests/utils/arbitraries.ts`（本番データの「形」を混ぜる）。

- 性質は md（この文書、Schema、§6 の決定）から立てる。**コードを読んでから立てると、バグに合わせた性質になる**。
- 条件を満たす入力だけで確かめる性質は、条件を満たした件数も検査する。最初の版では更新の検査を通る入力が 3000 件中 64 件しかなく、ほとんど何も確かめていなかった。
- 失敗したら、fast-check が縮めた最小の反例が出る。md に根拠があれば実装のバグ、なければ仕様の穴として人間が判断する。
- 今ある性質: 日付計算、どんなドキュメントでも読めたら配列の長さが正しく値は許容値（読めなければ `FIRESTORE_DATA_CORRUPTION` だけ）、検査を通った更新は消えない、配列の伸び縮み、部屋の状態と重複、宿泊税の集計。

### 3.6 実機確認と探索的テスト

単体テストや mock を使ったテストは「テストは通るのにアプリは動かない」状態を見逃す。実例: `.env.development` のキー名の不一致でログイン API が 503 だったが、テストは `verifySession` を mock しているので通っていた（#15）。

- env、認証、DB、SSR、CSP など **境界に触れる変更** では、Emulator 環境（`make`）でアプリを起動して変更箇所を実際に操作し、証拠（画面、HTTP レスポンス、ログ）を残す。Claude Code では `run` スキルを使う。
- 探索的テストは、チャーター（狙い）を決めて Playwright などで操作する。判定基準は「ユーザーならこう動くと期待する」という常識。2026-10-31 に一巡したチャーター:
  - C/O 日を DatePicker にキーボードで直接入力し、C/I 日以前・同日・遠い未来にする
  - 泊数を伸ばす・縮めて、各泊の入力が保存後も残るか
  - 大人の人数を 0・9 にして、年代の入力がどうなるか
  - 同じ予約を2タブで開いて編集する。保存中にモーダルを閉じる。ネットワークを切る
  - キャンセル → 復活 → キャンセルを繰り返す。キャンセル済みの予約を編集する
  - 月をまたぐ連泊を、宿泊税テーブル・清掃ボード・タイムテーブルで見る
  - 部屋未定の予約、同じ部屋・同じ日に2件ある予約を見る
  - 宿泊税テーブルを月初・月末・JST 6:00〜9:00 に、ブラウザの TZ を変えて開く
  - 印刷で情報が欠けないか（長いゲスト名、7部屋すべて埋まった日）
- サーバーの時刻を変えて動かす手段はないので、時刻に依存する確認は §3.4 のテストで行う。ブラウザ側は Playwright の `timezoneId` と `page.clock` で確かめられる。
- 前提: **本番の Firestore に対して操作しない。** Emulator と匿名化データ・人工データ（`docs/LocalDevelopment.md` §8）を使う。操作で変えたデータは `make seed` で戻す。

### 3.7 状態遷移と競合

- 予約の状態（通常・キャンセル済み）× 操作（編集・キャンセル・復活・宿泊税チェック）を、各操作2回・存在しない予約も含めて Emulator で確かめる。

  | 状態 | 編集 | キャンセル | 復活 | 宿泊税チェック |
  |---|---|---|---|---|
  | 通常 | 200 | 200（2回目は 409） | 409 | 200 |
  | キャンセル済み | 200 | 409 | 200（2回目は 409） | 200 |
  | 存在しない | 404 | 404 | 404 | 404 |

- 自動保存は E2E で、debounce 中に閉じる・保存失敗後に再編集する・前の保存の応答が遅い、を再現する。
- 同時編集（楽観ロック）は入れていない（#13、§6）。

### 3.8 本番の観測

- ALERT（Slack）は「人が対応しないと直らない障害」に限る。入力が原因のものは 4xx にして通知しない（`docs/ErrorHandling.md`）。
- 壊れた予約の読み飛ばしは WARN ログ（件数・ID・理由）に残し、Slack には通知しない。Cloud Logging で検索・集計でき、Gmail 取り込み側のバグの検出にも使える。
- ログは `logger` の第1引数が本文（どの処理の何のログか）で、元の例外は `cause` に入る。

## 4. 再発防止と横展開

- 見つけたバグは、直すときに必ず **最小の再現ケースを回帰テストとして追加** し、修正前に落ちることを確かめる。
- 回帰テストの役割は仕様の正しさの保証ではなく、**直したバグを戻さないこと** と割り切る。

| バグの場所 | 回帰テストの置き場 |
|---|---|
| Domain、純粋関数 | `tests/unit/` |
| Infra の変換（`toReservation` など） | `tests/unit/`（export して純粋関数として） |
| Route Handler の入力検証・status | `tests/integration/` |
| Firestore に書いて読む経路、状態遷移 | `tests/emulator/` |
| 時刻・TZ に依存する処理 | `tests/time/` |
| 画面操作、自動保存 | `e2e/` |

直したら、原因のパターンで全体を grep する。このプロジェクトで見つかったパターン:

| パターン | 例 |
|---|---|
| 入口の Zod に refine がない（日付の前後、実在日、範囲、許容値、配列の長さ） | #3, #6, #7, #12 |
| 読み取りの正規化（fallback・読み飛ばし）が、書き込みの失敗や破損を黙って隠す | #4, #6, #10 |
| `request.json()` を catch していない | #1 |
| 実行環境のローカル時刻に依存している（`new Date()` の `getMonth()` / `getDate()`、`toISOString()`、`new Date('YYYY-MM-DD')`）。サーバーもブラウザも | #8, #9, #21 |
| 外部エラーを「その他はすべて障害」「`auth/` はすべて未ログイン」と分類している。同じコードが入力の誤りにも障害にも使われる（`auth/argument-error`） | #2, #5, #23 |
| 外部呼び出しを try の外で行い、障害が共通のエラー処理を通らない | #23 |
| ログの付加情報が本文や元の例外を消す | #16, #20 |
| UI の入力欄が、入力途中の値を変更として通知する | #17, #19 |
| 失敗した保存を捨てる、保存の応答を待たずに次を送る | #24, #28 |
| `FieldValue.arrayUnion` が同じ内容の要素を追加しない | #25 |
| 今の状態を確かめずに状態を変える（古い画面からの操作） | #27 |
| 画面から使われていないコード（常に同じ引数で呼ばれる分岐など）にバグが残る | #9, #22 |

## 6. 仕様として決めたこと（2026-10-31）

| 項目 | 決定 | 理由 |
|---|---|---|
| 予約の更新の検査（#3, #6） | 読み取り・検査・書き込みを `runTransaction` で囲む。泊数・大人の人数が変わるのに配列が揃っていなければ 400。DB の C/O が壊れている予約も、正しい C/O と配列を送れば直せる | 検査と書き込みの間の別の更新で、長さの合わない配列が書かれないように |
| 書き込みの日付の範囲（#7） | 実在日に加えて、今日から 100 日前〜365 日後の範囲も検査する | 画面からは範囲外の予約を開けないので実害はなく、年の打ち間違いを止められる |
| 泊数の上限（#12） | 30 泊 | 画面の取得窓（前後 30 日の C/I）を超える滞在は表示されない。本番の 486 泊の手動追加の予約は誤入力か部屋の押さえと見て、読み飛ばしにした |
| 壊れた予約の読み飛ばし（#10） | WARN ログだけ。Slack には通知しない | データの異常は障害ではなく、通知すると本物の障害が埋もれる |
| ダブルブッキング（#11） | ダッシュボードに警告。保存は止めない | 予約の大半は Gmail 取り込みが書くので、このアプリだけでは止められない |
| 同時編集（#13） | 現状維持 | 同じ予約を同時に開くことはまれ |
| 時間帯制限（#14） | 本番はログイン API も時間外は 403。他の API は制限しない | 他の API は Session Cookie が 23:00 に切れる |
| 保存の失敗（#24） | 通信エラー・5xx は送り直し、それでも失敗したら閉じる前に確認。400・404 は送り直さない | 送り直しても通らないものを送り続けると閉じられなくなる |
| 部屋未割り当て（#26） | 現状維持 | 当日までに部屋を割り当てる運用 |
| すでにその状態のキャンセル・復活（#27） | 409。履歴も通知も増やさない | 古い画面で操作していたことに気付ける |
| キャンセル済みの予約の編集・宿泊税チェック | できる（200） | キャンセル理由のメモや、復活前の修正に使える。宿泊税テーブルはキャンセル済みを表示しない |
| 操作履歴（`mail_memo`）の編集・削除 | 画面から追加・編集・削除（確認あり）でき、システムの記録も消せる | 画面に削除ボタンと確認があり、意図した仕様 |
| 月をまたぐ連泊の宿泊税 | 全泊分を C/I の月に計上する | 宿泊税は C/I 時にまとめて受け取る |
| Slack の通知先 | 障害（`[ALERT]`）と、手動の追加・キャンセル・復活の記録だけ | 入力の誤り（4xx）、ログインの失敗、データの異常は通知しない |

## 7. 残っていること

人の判断・作業が必要なもの:

- **486 泊の予約**: 本番の `guestInfoV2` に、2025-04-01 → 2026-07-31（手動追加・キャンセルなし）の予約が1件ある。泊数の上限で読み飛ばされ、WARN ログに残る。本番の Firestore で直すか削除するかを決める。
- **清掃ボードの印刷**: 縦書きの列見出し（シャンプー、歯ブラシ等など）が、画面幅 1400px の印刷モードの画像では切れて見えた。実際の用紙に印刷して確かめる。

現状維持にしたもの（`docs/KnownIssues.md`）: 同時編集（#13）、部屋未割り当ての予約がタイムテーブルと清掃ボードに出ない（#26）。

今後:

- 機能を追加・変更したら、§4 の回帰テストと横展開を行い、関連する §3.6 のチャーターを実機で再実行する。
- 境界（env・認証・DB・SSR・CSP）に触れる変更は、Emulator で実際に動かして確かめる。
- 新しいバグを見つけたら §5 に行を足し、原因のパターンが新しければ §4 にも足す。
