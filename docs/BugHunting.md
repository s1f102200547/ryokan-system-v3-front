# Bug Hunting Strategy

テストの目的を「品質の保証」ではなく「バグの発見」と「発見済みバグの再発防止」に置く。各手法を **課題 → 解決策** の形でまとめる。

基本サイクル:

```
探索でバグを見つける → 直す → 回帰テストにする → 同じ原因の箇所を横展開で探す
```

---

## 0. 前提: テストの期待値が「なぞり」になる

### 課題

- 仕様 md もコードも AI と一緒に書いているため、期待値を md から取ってもコードから取っても **同じ解釈をなぞるだけ** になる。md の穴や誤解はそのままコードとテストに写り、テストはすべて通る。
- 実例: `tests/integration/` の Route テストは Application 層を丸ごと `vi.mock` している。そのため、Route の Zod、Infra の Zod、TS 型の食い違いから起きるバグ（git 履歴で最も多かった種類）を構造的に検出できない。
- 過去のバグの多くは、テストではなく **人が実際にアプリを使って** 見つけている（旧 `GuestInfoFix.md` の「未定と表示されない」「大人 0 人で保存失敗」など）。

### 解決策

- 期待値を md やコードから取らない手法を併用する。判定の基準は次の4つ。

| 判定の基準 | 手法 |
|---|---|
| 実際に動いているアプリ | 1. 実際に動かして確かめる |
| 過去のバグ | 2. 横展開 |
| 「落ちてはいけない」という最低限のルール | 3. ファジング |
| 単純な不変ルールと仕様の穴 | 4. PBT |
| ユーザーの常識 | 5. 探索的テスト |

- 仕様そのものの誤り（作るべきものが違う）は、どの手法でも見つからない。自分で使うことと、現場のスタッフに触ってもらうことで補う。

---

## 1. 実際に動かして確かめる

### 課題

単体テストやモックを使ったテストは関数の結果しか見ないため、「**テストは通るのにアプリは動かない**」状態が起きる。

- 実例 (2026-10-31): `.env.development` のキー名が `NEXT_PUBLIC_FIREBASE_PRIVATE_KEY` になっており、`src/lib/firebase/admin.ts` が読む `FIREBASE_PRIVATE_KEY` と一致していなかった。admin SDK が ADC に fallback して `Unable to detect a Project Id` となり、ログイン API が 503 を返していた。テストは `verifySession` をモックしているため、すべて通っていた。

### 解決策

- env、認証、DB、SSR、CSP など **境界に触れる変更** では、アプリを起動して変更箇所を実際に操作し、証拠（画面、HTTP レスポンス、ログ）を残す。Claude Code では `run` スキルを使う。
- 「今変えた箇所」の確認なので、仕様の誤りは見つけられない点に注意する。

---

## 2. 横展開

### 課題

1つのバグを直しても、**同じ原因のバグが別の場所に残る**。git 履歴では、同じ制約（`adult_count` の下限、`room` の null、`''` と `null`、日付の書式）が Route の Zod、Infra の Zod、TS 型、DB の実データの4か所に分かれて書かれており、1か所だけ直すパターンが繰り返されていた。

- 実例: 予約の新規追加 `POST /api/reservations` には `check_out_date > check_in_date` の refine があるが、更新 `PATCH /api/reservations/[id]` にはない。チェックアウト日をチェックイン日以前に変更できる。

### 解決策

- バグを直したら、**原因のパターン**（例: 「入口の Zod に refine がない」「`request.json()` を catch していない」）を言語化し、コード全体から同じパターンを洗い出す。
- 根本対策として、同じ制約を1か所のスキーマに集約し、Route と Infra の両方がそれを参照する形にする。

---

## 3. ファジング

### 課題

テストは「まともな入力」しか試さないため、**変な入力で壊れる箇所** が残る。

- 実例 (2026-10-31、dev サーバーで確認):
  - `POST /api/auth/login` に壊れた JSON または空の body を送ると **HTTP 500**。`src/app/api/auth/login/route.ts` の `request.json()` に catch がない（他の Route は `.catch(() => null)` 済み）。
  - 形式が不正な idToken を送ると、`auth/argument-error` が `CREDENTIAL_ERROR_CODES` に含まれないため **503 + Slack [ALERT]** になる。不正な入力だけで障害通知を大量に発生させられる。

### 解決策

- 全 Route Handler に対して、空、型違い、巨大な値、負の数、不正な JSON、不正な日付をランダムに送るテストを書く。
- 判定の規則は仕様の中身に依存しないものにする: **「どんな body、query、params でも 5xx を返さない（4xx で拒否する）」**。インフラ障害の 503 は正しい挙動なので、ファジングではインフラ層をモックし、入力起因の 5xx だけを検出する。
- 書き込み API は DB を変更するため、モックまたは Firestore Emulator 上で実行する。

## 4. PBT（Property-Based Testing）

### 課題

- 具体的な期待値を書くテストは、書いた人の想定した入力しか試さない。
- AI に性質を考えさせると誤報が大量に出る。コードから性質を考えさせると、バグに合わせた性質になる。

### 解決策

- md から **単純で一般的な性質** を立て、fast-check で大量の入力を試す。このプロジェクトの候補:
  - 泊別配列（`dinner_time` など）の長さは常に泊数と一致する
  - `dateDiff(a, addDays(a, n)) === n`
  - Route の Zod が受け付けた値を `updateReservation` で書き、`toReservation` で読み戻しても壊れない
  - 同じ部屋・同じ夜に有効な予約は2件以上存在しない
- 失敗したら「実装のバグか、性質の立て方の誤りか」を md を根拠に判定する。**md に根拠が見つからなければ仕様の穴** として人間が判断する。
  - 実例: ダブルブッキングの検査はコードにも md にもない。仕様として許すかどうかは未決定。
- 報告の半分近くが誤報になりうるため、最終確認は人間が行う。ドメインが小さいので、2・3 の後に着手する。

## 5. AI エージェントによる探索的テスト

### 課題

テストは md やコードに書かれたケースしか試さないため、**誰も想定していなかった使い方** で起きるバグが見つからない。

### 解決策

- AI にブラウザでアプリを触らせ、「ユーザーならこう動くと期待する」という常識を基準に、おかしな挙動を報告させる（Playwright MCP とチャーター）。
- 実行ごとに動きが変わるため、報告されたバグは再現を確認してから直し、回帰テストにする。
- 前提条件:
  - **本番の Firestore に対して書き込み操作をさせない。** Emulator または専用環境と、ダミーデータを用意してから行う。
  - 予約データにはゲストの個人情報が含まれるため、実データを使わない。

---

## 6. 発見したバグの再発防止

### 課題

探索的な手法は毎回結果が変わるため、見つけたバグを記録しないと同じバグがまた入る。AI が高速にコードを書き換える開発では、再発のリスクが高い。

### 解決策

- 見つけたバグは、直すときに必ず **最小の再現ケースを回帰テストとして追加** する（Domain なら `tests/unit/`、Route なら `tests/integration/`、画面操作なら `e2e/`）。
- 回帰テストの役割は仕様の正しさの保証ではなく、**直したバグを戻さないこと** と割り切る。

---

## 7. 本番の観測

### 課題

本番のユーザー操作は最強のバグ発見手段だが、今は不正な入力でも Slack [ALERT] が鳴るため、本物の障害がノイズに埋もれる。

### 解決策

- 入力起因のエラーは 4xx にして ALERT を鳴らさず、ALERT は「人が対応しないと直らない障害」に限定する（`docs/ErrorHandling.md` の方針どおり）。
- ログイン失敗の WARN ログは、ブルートフォース検知（`docs/KnownIssues.md`）にも使う。

## 発見済みの課題（2026-10-31 時点）

| # | 課題 | 発見した手法 | 状態 |
|---|---|---|---|
| 1 | `POST /api/auth/login` が不正な JSON と空の body で 500 | ファジング | 未対応 |
| 2 | 不正な idToken で 503 + Slack [ALERT] | ファジング | 未対応 |
| 3 | `PATCH /api/reservations/[id]` で `check_out_date <= check_in_date` を許す | 横展開 | 未対応 |
| 4 | ダブルブッキングの検査がない（仕様の穴の可能性） | PBT の性質検討 | 仕様の判断待ち |
| 5 | `.env.development` のキー名の不一致でログイン不可 | 実際に動かす | 開発環境の Emulator 化で解消（鍵を置かない。名前に `PRIVATE_KEY` を含む変数は起動ガードで拒否。`docs/LocalDevelopment.md`） |

## 進め方

1. 発見済みの課題 1〜3 を直し、それぞれ回帰テストにする。4 は仕様を決める。
2. 全 Route Handler 共通のファジングテストを追加する。
3. Route の Zod、Infra の Zod、TS 型の制約の食い違いを横展開で洗い出す。
4. 境界に触れる変更では、実際に動かして確かめる。
5. 探索的テストと PBT に進む。前提の Emulator と匿名化データ（人工データ）は用意済み（`make`。`docs/LocalDevelopment.md` §8）。
