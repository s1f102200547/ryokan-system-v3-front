- GCP・GitHub・Firebase の管理画面の設定はコードにないので、文書の記述を正しいものとして評価した。`gmail-listener` は別リポジトリなので、現状は「不明」
- 起こりやすさ・被害・効き目・現状の点数はどれも見立て。実情に合わなければ直す
- 解決策の「SI n」は [SecurityImplementation.md](SecurityImplementation.md) の項番

## 1. 評価の方法

### 防御フェーズ

| フェーズ | 意味 |
|---|---|
| 入口に届かせない | 攻撃面を減らす |
| 突破を防ぐ | 脅威を成立させない |
| 被害を限定 | 守るものへの到達 |
| 気付く | 検知・通知 |
| 戻す | 失効（漏えいを止める）・復旧（データを戻す） |

### 優先度（現状を見ずに決める）

**優先度 = 本来のリスク × 効き目**（1〜27）

- 本来のリスク = 起こりやすさ（1〜3）× 被害（1〜3）。防御がないとしたときの値（Security.md §1）
- 効き目（1〜3）: そのフェーズで守ることが、その経路にどれだけ効くか。今の実装は見ずに、経路とフェーズの組だけで決める
  - 3: その段で止めるのが本筋 / 2: 補助として効く / 1: その経路にはあまり効かない
  - 効き目 3 は1つの経路に2つまで（本筋が3つ以上あると差が付かない）
  - 「戻す」は失効と復旧に分けて考える。失効（今続いている漏えいを止める）は、認証情報が盗まれる経路で 2〜3。復旧（消された・書き換えられたデータを戻す）は、漏えいが主な経路では 1（漏れた情報は戻せない）、削除・改ざんがありうる経路では 2〜3
  - 「こちらで手を出せるか」は効き目に入れず、**実行の制約**として別に書く（例: 旅館の PC は旅館の管理）
- 段階: 24 以上 = 最優先、18 以上 = 優先、12 以上 = 中、それ未満 = 低

### 現状と差

| 現状 | 意味 |
|---|---|
| 3 強 | 単独でも止まる |
| 2 中 | 効くが抜け道がある |
| 1 弱 | 部分的・人頼み |
| 0 なし | — |
| 不明 | 別リポジトリなどで見えない。差の計算では弱（1）として扱う |

**差 = 優先度 ×（3 − 現状）**（0〜81）。着手の順を決める値。優先度が高く現状が強のセルは差が 0 になるので、§5 で「維持する対策」として別に挙げる。

## 7. 経路ごとの詳細

### 3. 旅館の PC の感染によるパスワード・Cookie の窃取

- 攻撃者: 業界を狙う犯罪者
- 経路: 旅館の PC（マルウェア） → パスワード・Cookie の窃取 → 宿泊客の個人情報
- 本来のリスク: 高 9（起こりやすさ 3 × 被害 3）。宿泊業は予約サイトを装ったフィッシングとインフォスティーラーの標的になりやすい。PC の管理はこちらの手の外
- 見立て: 起こりやすさ（インフォスティーラーは宿泊業でも多い）× 被害（高）が最も大きいのに、全フェーズが弱以下。MFA を入れてもパスワードの悪用が止まるだけで、Cookie の再利用は残る。

#### 入口に届かせない — 優先度 18（優先）／ 現状 なし ／ 差 54

- 効き目 2: PC の衛生は根本だが、盗まれたあとの段が別にあるので補助
- 実行の制約: PC は旅館の管理で、こちらからは依頼しかできない
- 対策: なし
- 穴: PC の OS・ブラウザ・メールは旅館側の管理で、このアプリからは手を出せない（前提）
- 解決策: 旅館に1枚の依頼書を渡す：Defender の有効化、OS とブラウザの自動更新、業務 PC で私用のメール・サイトを開かない

#### 突破を防ぐ — 優先度 27（最優先）／ 現状 なし ／ 差 81

- 効き目 3: 盗まれたパスワード・Cookie だけでは入れなくするのが一番効く
- 対策: Cookie は HttpOnly・SameSite=Strict（XSS や他サイトからの送信は防ぐ）

- 解決策: MFA で、パスワードだけでは入れなくする（SI 2）。SMS を受ける電話を決めておく（PC 単位のアカウントを全員で使うため） / 候補として、端末に結び付いた認証（Windows Hello・パスキー）と比べる。Firebase Auth の標準の MFA にはないので自前になる / Cookie は MFA 後も盗める。これは「被害を限定」の側で手当てする

#### 被害を限定 — 優先度 18（優先）／ 現状 弱 ／ 差 36

- 効き目 2: セッションの短さや接続元の固定で、盗まれたあとの使い道を狭める

### 2. Identity Toolkit へのパスワードの総当たり

- 攻撃者: 無差別な自動攻撃・業界を狙う犯罪者
- 経路: Identity Toolkit → 総当たり → 宿泊客の個人情報
- 本来のリスク: 中高 6（起こりやすさ 2 × 被害 3）。メールアドレスが分からないと始まらないが、Identity Toolkit は誰でも呼べる
- 見立て: パスワードの強さ1つで持っている行。アプリ側は失敗を見ることもできない。

#### 入口に届かせない — 優先度 12（中）／ 現状 弱 ／ 差 24

- 効き目 2: ログインの口を公開しないで済めば総当たり自体ができない
- 対策: 新規登録は API からも無効であることを確認済み
- 穴: API キーはブラウザに埋め込まれ、Identity Toolkit は誰でも呼べる（ログインのサーバー経由化は §8 未着手）
- 解決策: ログインをサーバー経由にし、API キーをサーバー専用にする（SI 3） / それまでは API キーを Identity Toolkit だけに制限し、リファラーを本番の URL に絞る

#### 突破を防ぐ — 優先度 18（優先）／ 現状 中 ／ 差 18

- 効き目 3: 強いパスワードと MFA で突破を止めるのが本筋
- 対策: パスワードは openssl で生成した長いもの。総当たりは現実的でない / 時間外は /api/auth/login が 403
- 穴: MFA がない（§8 未着手） / アプリ側の失敗回数の制限がない。Firebase の標準の制限だけ（§8 未着手） / ログイン API でパスワードの長さを確かめていない（§8 未着手）
- 解決策: MFA（SI 2）。SMS は送信料と不正な大量送信（SMS pumping）があるので、送り先を日本に限り、TOTP も比べる / サーバー経由にしたあと、メールと IP ごとの失敗回数で 429（SI 3）

#### 被害を限定 — 優先度 12（中）／ 現状 中 ／ 差 12

- 効き目 2: 権限や読み取りの範囲を絞れば、破られたアカウントでできることが減る
- 実行の制約: ロールなし（スタッフ全員が全機能を使う）は前提
- 対策: セッションは当日 23:00 まで / 時間外にはログインできない
- 穴: 突破されれば全機能（ロールなし。前提として受容）
- 解決策: MFA が入れば現状で足りる（ロールなしは前提）

#### 気付く — 優先度 12（中）／ 現状 弱 ／ 差 24

- 効き目 2: 失敗の急増や知らない場所からのログインに気付ける
- 対策: ログイン成功のたびに Slack にアカウント・IP・ブラウザが出る
- 穴: 失敗はブラウザと Google の間で完結し、アプリから見えない
- 解決策: サーバー経由にしたあと、ログイン失敗の急増を Slack に通知する

#### 戻す — 優先度 12（中）／ 現状 弱 ／ 差 24

- 効き目 2: 破られたアカウントの失効とパスワードの作り直し
- 対策: Firebase 側でセッションを失効させれば、次の API から 401 になる
- 穴: パスワードの変更機能はない。失効の手順は文書にない
- 解決策: セッション失効の手順書を作る（コンソールでのユーザーの無効化、または revokeRefreshTokens）

### 7. npm・GitHub Actions の悪性バージョンの混入

- 攻撃者: 開発者を狙う攻撃者・無差別な自動攻撃
- 経路: 依存パッケージ・Actions → 悪性バージョン → 個人情報・管理権限
- 本来のリスク: 中高 6（起こりやすさ 2 × 被害 3）。npm の乗っ取りは毎年起きている。本番で動けば Firestore 全体を読める
- 見立て: 入口は全体で一番厚い。入られた後（サーバーで動く悪性コード）を止めるものは少ない。

#### 入口に届かせない — 優先度 18（優先）／ 現状 強 ／ 差 0

- 効き目 3: 悪性の版を取り込まないのが本筋
- 対策: Actions・ツール・Docker イメージを SHA / digest で固定 / 公開から7日未満の版を入れない / install スクリプトは allowScripts のものだけ（今は全部 false） / Dependabot は週1回でまとめて PR
- 穴: なし
- 解決策: 現状維持。Dependabot の PR では lockfile に新しく入るパッケージを見る

#### 突破を防ぐ — 優先度 12（中）／ 現状 中 ／ 差 12

- 効き目 2: 取り込んでも CI やビルドで動かさない
- 対策: CI の権限は読み取りだけ（ZAP の Issue を除く） / GCP の認証は main の deploy.yml だけ
- 穴: 悪性コードがビルドに入れば本番で動く。止めるのはレビューだけ
- 解決策: 新しい依存を入れる前に、メンテナー・公開日・install スクリプトを確かめる（今の方針を続ける）

#### 被害を限定 — 優先度 18（優先）／ 現状 中 ／ 差 18

- 効き目 3: 本番で動いたときに、何を読めて外に出せるかで被害が決まる
- 対策: ブラウザ側は CSP で外への通信を禁止 / 実行 SA の権限は最小、コンテナは非 root
- 穴: サーバー側の外への通信は制限していない（Cloud Run の egress） / 実行 SA は Firestore 全体を読める
- 解決策: Cloud Run の外への通信を VPC 経由にし、Google の API と Slack 以外を止める（費用と手間があるので優先度は低め）

#### 気付く — 優先度 12（中）／ 現状 弱 ／ 差 24

- 効き目 2: 悪性のパッケージの報告に早く気付く
- 対策: npm audit（high 以上）
- 穴: audit は既知の脆弱性だけで、悪性コードは見つけない
- 解決策: 任意：悪性パッケージを検知するサービスを Dependabot の PR に入れる

#### 戻す — 優先度 6（低）／ 現状 弱 ／ 差 12

- 効き目 1: 漏れた情報は戻せない
- 対策: イメージを SHA で残しているので前の版に戻せる
- 穴: データのバックアップがない
- 解決策: Firestore のバックアップ

### 8. 依存パッケージの既知の脆弱性の悪用

#### 入口に届かせない — 優先度 12（中）／ 現状 中 ／ 差 12

- 効き目 2: 脆弱な版を早く外すことで攻撃面が減る
- 対策: Dependabot の週1回の更新 / 悪用中のものは7日待たずに上げる手順がある
- 穴: セキュリティ更新の自動 PR は無効（main 宛てにしか作れないため）

#### 突破を防ぐ — 優先度 18（優先）／ 現状 中 ／ 差 18

- 効き目 3: 既知の脆弱性は直すことが本筋

- 穴: moderate は失敗しない（§10 に記載済み）

#### 被害を限定 — 優先度 12（中）／ 現状 中 ／ 差 12

- 効き目 2: 突かれても権限が小さければ被害は限られる
- 対策: 実行 SA の最小権限、非 root、standalone の最小イメージ
- 穴: 経路1と同じく Firestore 全体が読める
- 解決策: 経路1と同じ（日付の範囲を狭める、一覧から mail_memo・メモを外す、読み取りの上限）

#### 気付く — 優先度 12（中）／ 現状 弱 ／ 差 24

- 効き目 2: デプロイ済みの版が脆弱だと分かること
- 対策: CI で毎回 audit
- 穴: デプロイ済みのイメージに後から見つかった脆弱性は、次の push まで検査されない
- 解決策: CI に週1回の定期実行を足し、デプロイ済みの版の audit を走らせる

#### 戻す — 優先度 6（低）／ 現状 弱 ／ 差 12

- 対策: 前のイメージに戻せる
- 穴: データのバックアップがない
- 解決策: Firestore のバックアップ

### 4. 旅館の PC からの盗み見・持ち出し・Cookie のコピー（受容）

- 経路: 旅館の PC → 盗み見・持ち出し → 個人情報・宿泊税の記録
- 本来のリスク: 中 3（起こりやすさ 1 × 被害 3）。スタッフは少人数で顔見知り。起きれば個人情報が出る
- 見立て: 正規の利用者なので止めにくく、人単位の認可・監査は作らないと決めている。受容しているリスクとして明示しておくとよい。

#### 入口に届かせない — 優先度 3（低）／ 現状 弱 ／ 差 6

- 効き目 1: 正規の利用者なので、入口では区別できない
- 実行の制約: 正規の利用者
- 対策: アカウントは PC 単位
- 穴: 正規の利用者で、入口では区別できない
- 解決策: 受容（人単位のアカウントは作らない前提のまま）

#### 突破を防ぐ — 優先度 6（低）／ 現状 弱 ／ 差 12

- 効き目 2: パスワードを人に見せない・持ち出させない工夫
- 対策: パスワードは自動入力で、スタッフが値を覚えていない
- 穴: パスワードマネージャーからは表示できる（OS のパスワードを求められる程度） / Cookie を別の PC にコピーすれば使える
- 解決策: PC ごとに Windows のログインにパスワードを付け、パスワードマネージャーが表示の前に OS の認証を求める設定か確かめる

#### 被害を限定 — 優先度 9（低）／ 現状 弱 ／ 差 18

- 効き目 3: 一度に見られる・出せる量を絞るのが本筋
- 対策: 返す範囲を日付と表の項目に限定
- 穴: ロールなし。ログインできれば全機能（受容）
- 解決策: 受容。CSV を先月分・表の項目だけに保つ（今どおり）

#### 気付く — 優先度 9（低）／ 現状 なし ／ 差 27

- 効き目 3: 内部の不正は記録があることが一番の抑止になる
- 対策: なし
- 穴: 人単位の監査は作らないと決めた（受容） / 誰がいつどの予約を見たかは残らない
- 解決策: 任意：どの PC アカウントが何件読んだかをログに残す（PC 単位なので方針と矛盾しない）

#### 戻す — 優先度 3（低）／ 現状 弱 ／ 差 6

- 効き目 1: 持ち出された情報は戻せない
- 対策: キャンセル・復活・手動追加は mail_memo に履歴が残る
- 穴: 通常の編集の履歴はない。バックアップもない
- 解決策: バックアップ（経路1の「戻す」）があれば、改ざん・削除の前の状態に戻せる

## 8. 読み取れること

### 強いところ（維持する）

- 公開 URL の「突破を防ぐ」（優先度 27・現状 強）: 全11 API の `requireSession`（失効の確認つき）、Zod と上限、nonce の CSP、Semgrep・ZAP・fuzz
- 悪性バージョンの「入口に届かせない」（優先度 18・現状 強）: SHA 固定、`min-release-age=7`、`strict-allow-scripts`
- Git への混入: 5フェーズすべてが中以上

### 差が大きいところ（足す）

- 旅館 PC の感染: 「突破を防ぐ」の差が 81 で最大。入口・気付く・戻すも上位。MFA だけでは盗まれた Cookie が残るので、MFA・Cookie と IP の結び付け・失効の手順書を一式で設計する
- 公開 URL の「被害を限定」: 1つのセッションで約465日分の予約を読める。日付の範囲を狭め、一覧から mail_memo・メモを外す
- 管理者アカウントの乗っ取りの「戻す」: バックアップがなく、消されたら戻せない（差 54）
- gmail-listener: 現状が見えないので、弱として計算した値で上位にいる。実際の状態を確かめるまで残る

### 脅威モデルの外にあるもの・注意

- 漏えい時の報告義務: 個人情報保護法では、不正アクセスによる漏えいは個人情報保護委員会への速報（概ね3〜5日以内）・確報と、本人への通知が要る。漏えいの経路の「戻す」は、事故対応の手順書として中身を持てる
- Slack: ログインの通知（アカウント・IP）とエラーの文が集まる。エラーの文に氏名・メモが入らないかを確かめる。Webhook の URL は環境変数（§8 後回し）
- 可用性・請求: §3 の守るものに入っていない。SMS の MFA は SMS の費用と不正な大量送信（SMS pumping）の面を増やす
- ログを足すと、Cloud Logging に IP などの個人情報が増える。保持期間と、ログを読める人を決める
- ZAP に認証を渡して能動的な検査をするときは、書き込みが起きるので Emulator とテストデータに向ける
- 開発者が1人なので、Environment の承認は「一度止まる」だけ。gh の認証を奪われると API から承認もできる。gh のトークンの権限と期限を絞るほうが効く
- ログアウトがなく、セッションを失効させる手順も文書にない（`verifySession` は `checkRevoked=true` なので、Firebase 側で失効させれば次の API から 401 になる）
