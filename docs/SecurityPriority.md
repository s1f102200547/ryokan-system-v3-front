# Security Priority（攻撃経路 × 防御フェーズの優先度）

[Security.md](Security.md) の「想定する攻撃者 → 入口 → 脅威 → 守るもの」を10本の攻撃経路にし、5つの防御フェーズごとに優先度と現状を評価したもの。2026-11-07 時点。

- 根拠: [Security.md](Security.md)・[Development.md](Development.md)・[SecurityImplementation.md](SecurityImplementation.md)、`src/proxy.ts`、`src/app/api/**/route.ts`、`src/lib/auth/`、`src/lib/api/routeHelpers.ts`、`src/lib/csp.ts`、`firestore.rules`、`.github/workflows/*.yml`、`.claude/settings.json`、`.npmrc`、`Dockerfile`
- GCP・GitHub・Firebase の管理画面の設定はコードにないので、文書の記述を正しいものとして評価した
- 起こりやすさ・被害・効き目・現状の点数はどれも見立て。実情に合わなければ直す
- 解決策の「SI n」は [SecurityImplementation.md](SecurityImplementation.md) の項番

## 1. 評価の方法

### 防御フェーズ

| フェーズ | 意味 |
|---|---|
| 入口に届かせない | 攻撃面を減らす |
| 突破を防ぐ | 脅威を成立させない |
| 被害を限定 | 守るものへの到達 |
| 気付く | 検知・通知 |
| 戻す | 失効・復旧 |

### 優先度（現状を見ずに決める）

**優先度 = 本来のリスク × 効き目**（1〜27）

- 本来のリスク = 起こりやすさ（1〜3）× 被害（1〜3）。防御がないとしたときの値（Security.md §1）
- 効き目（1〜3）: そのフェーズで守ることがその経路にどれだけ効くか。今の実装は見ずに、経路とフェーズの組だけで決める
  - 3: その段で止めるのが本筋 / 2: 補助として効く / 1: その経路にはあまり効かない
  - 情報の漏えいは後から取り戻せないので、漏えいが主な経路の「戻す」は 1〜2
- 段階: 24 以上 = 最優先、18 以上 = 優先、12 以上 = 中、それ未満 = 低

### 現状（優先度とは別に評価）

| 点 | 意味 |
|---|---|
| 3 強 | 単独でも止まる |
| 2 中 | 効くが抜け道がある |
| 1 弱 | 部分的・人頼み |
| 0 なし | — |

優先度が高く現状が強のセルは「維持する対策」、優先度が高く現状が弱のセルは「足す対策」。

## 5. 経路ごとの詳細

### 3. 旅館の PC の感染によるパスワード・Cookie の窃取

- 攻撃者: 業界を狙う犯罪者
- 経路: 旅館の PC（マルウェア） → パスワード・Cookie の窃取 → 宿泊客の個人情報
- 本来のリスク: 高 9（起こりやすさ 3 × 被害 3）。宿泊業は予約サイトを装ったフィッシングとインフォスティーラーの標的になりやすい。PC の管理はこちらの手の外
- 見立て: 起こりやすさ（インフォスティーラーは宿泊業でも多い）× 被害（高）が最も大きいのに、全フェーズが弱以下。MFA を入れてもパスワードの悪用が止まるだけで、Cookie の再利用は残る。

#### 入口に届かせない — 優先度 18（優先）／ 現状 なし

- 効き目 2: PC の衛生が根本だが、こちらからは依頼しかできない
- 対策: なし
- 穴: PC の OS・ブラウザ・メールは旅館側の管理で、このアプリからは手を出せない（前提）
- 解決策: 旅館に1枚の依頼書を渡す：Defender の有効化、OS とブラウザの自動更新、業務 PC で私用のメール・サイトを開かない

#### 突破を防ぐ — 優先度 27（最優先）／ 現状 なし

- 効き目 3: 盗まれたパスワード・Cookie だけでは入れなくするのが一番効く
- 対策: Cookie は HttpOnly・SameSite=Strict（XSS や他サイトからの送信は防ぐ）
- 穴: パスワードはブラウザのパスワードマネージャーにあり、マルウェアは取り出せる / HttpOnly はインフォスティーラーには効かない / MFA なし、端末への結び付け（DBSC）は採用しなかった
- 解決策: SMS の MFA で、パスワードだけでは入れなくする（SI 2） / Cookie は MFA 後も盗める。セッションを数時間で切って再ログインにするかを検討する

#### 被害を限定 — 優先度 18（優先）／ 現状 弱

- 効き目 2: セッションの短さや接続元の固定で、盗まれた後の使い道を狭める
- 対策: Cookie は当日 23:00 で切れる / 時間外は画面もログインも使えない
- 穴: 盗まれたパスワードはどこからでも使える（IP 制限は採用しなかった）
- 解決策: MFA で旅館の外からのパスワードの利用を止める / Cookie を発行したときの IP と API の接続元 IP が違えば、拒否か通知にする

#### 気付く — 優先度 27（最優先）／ 現状 弱

- 効き目 3: 防ぎきれない前提なので、いつもと違う使われ方に気付くことが要
- 対策: 盗んだパスワードで旅館の外からログインすると、Slack に知らない IP が出る
- 穴: 盗んだ Cookie の再利用はログインを通らないので、通知されない / Slack の通知は人が見て気付く前提
- 解決策: API ごとに uid と接続元 IP をログに出し、ログイン時と違う IP からの呼び出しを Slack に通知する

#### 戻す — 優先度 27（最優先）／ 現状 弱

- 効き目 3: 気付いたらすぐに失効させられるかで被害の長さが決まる
- 対策: verifySession は checkRevoked=true。Firebase 側で失効させれば即時に効く
- 穴: アプリにログアウトも失効の操作もない / 感染時に何をするかの手順がない
- 解決策: 失効の手順書：どの PC のアカウントを失効させ、パスワードを作り直すか / 任意でログアウトボタン

### 1. 公開 URL からのコードの欠陥の悪用

- 攻撃者: 無差別な自動攻撃
- 経路: Cloud Run の公開 URL → コードの欠陥 → 宿泊客の個人情報
- 本来のリスク: 高 9（起こりやすさ 3 × 被害 3）。公開 URL は常に自動の探索を受ける。読まれれば個人情報が出る
- 見立て: 最も来やすい攻撃で、最も厚く守れている行。弱いのは復旧だけ。

#### 入口に届かせない — 優先度 18（優先）／ 現状 中

- 効き目 2: URL は公開が前提で、減らせる攻撃面は限られる
- 対策: 時間外（23:00〜6:00）は画面を /time-restricted に飛ばす / X-Powered-By を出さない、エラーに内部の詳細を出さない
- 穴: 公開（allUsers に run.invoker）は前提として必要 / proxy.ts の matcher は /api を含まないので、API の時間帯制限はログインだけ（Cookie が 23:00 で切れるので実害は小さい）
- 解決策: 必要なら proxy.ts の時間帯制限を /api にも広げる（Cookie の期限で実害は小さいので任意）

#### 突破を防ぐ — 優先度 27（最優先）／ 現状 強

- 効き目 3: 欠陥を突かせないことがこの経路の本筋
- 対策: 全11 API に requireSession（verifySessionCookie の失効確認つき）。ログイン API 以外に抜けはない / Zod と本番データの2〜5倍の上限、400 で検証の詳細を返さない / nonce + strict-dynamic の CSP、COEP/COOP/CORP、HSTS、frame-ancestors none / Semgrep・ZAP・fuzz（全 Route で 5xx を返さない）・PBT が CI で必須
- 穴: ZAP は Baseline で /login だけ。認証後の画面と API は動的検査していない
- 解決策: ZAP にログイン済みの Cookie を渡し、認証後の画面と API も検査する

#### 被害を限定 — 優先度 27（最優先）／ 現状 中

- 効き目 3: 1つの欠陥で全データに届くかどうかが被害の大きさを決める
- 対策: 実行 SA は Firestore の読み書きとセッションの発行・確認だけ / 日付は −100〜+365 日、宿泊税は今月・先月で表の項目だけ / Firestore Rules は全拒否（ブラウザから直接読めない）
- 穴: 1つのセッションで約465日分の予約（氏名・メモ）を順に読める / 実行 SA は Firestore 全体を読み書きできる（コレクション単位の制限はない）
- 解決策: API ごとに読んだ件数をログに出し、1セッションで異常に多い読み取りを Slack に通知する

#### 気付く — 優先度 18（優先）／ 現状 中

- 効き目 2: 探索や異常に気付ければ被害を早く止められる
- 対策: 5xx と InfraError は Cloud Logging と Slack に出る
- 穴: 400・401・404 の大量発生（探索）は通知しない
- 解決策: Cloud Logging のログベースの指標で、401・404 の急増にアラートを付ける

#### 戻す — 優先度 9（低）／ 現状 弱

- 効き目 1: 漏れた情報は戻せない。戻せるのは改ざん・削除だけ
- 対策: Cloud Run はステートレスで、イメージは SHA ごとに残る
- 穴: Firestore の PITR・削除保護・バックアップがない（§8 未着手）
- 解決策: Firestore の PITR・削除保護・毎日のバックアップを有効にし、別の DB への restore を1回試す（SI 1）

### 5. 開発者の PC の感染

- 攻撃者: 開発者を狙う攻撃者
- 経路: 開発者の PC（マルウェア） → 管理権限・ソース → 全部
- 本来のリスク: 中高 6（起こりやすさ 2 × 被害 3）。開発者を狙う悪性の拡張機能・パッケージは増えている。取られれば全部

- 効き目 3: 開発者の PC にマルウェアを入れないことが本筋
- 対策: VS Code の Workspace Trust、タスクの自動実行の停止
- 穴: 脅威の中身が未定義（§6 TODO）

- 穴: 上限に達すると業務も止まる
- 解決策: 最大インスタンス数で費用を抑え、予算の上限に届く前に頭打ちにする

#### 気付く — 優先度 4（低）／ 現状 中

- 効き目 2: 急増に気付ける
- 対策: 予算アラート / 5xx は Slack に出る
- 穴: 429 や大量の 401 は通知しない
- 解決策: 401・429 の急増にアラート（経路1の「気付く」と同じ）

#### 戻す — 優先度 4（低）／ 現状 中

- 効き目 2: 止まっても戻せる・紙で回せる
- 対策: ステートレスなので止めて戻せば復旧する
- 穴: 停止中の業務手順（紙の台帳など）は文書にない
- 解決策: 止まったときの紙の運用を決めておく（前日のタイムテーブルを印刷しておく、など）

## 6. 読み取れること

### 強いところ

- 公開 URL からの攻撃の「突破を防ぐ」: 全11 API の `requireSession`（失効の確認つき）、Zod と上限、nonce の CSP、Semgrep・ZAP・fuzz。優先度も最優先なので、維持する
- 依存パッケージ・Actions の「入口に届かせない」: SHA 固定、`min-release-age=7`、`strict-allow-scripts`
- Git への混入: gitleaks の全履歴の検査と、匿名化の許可リスト。5フェーズすべてが中以上

### 弱いところ

- 旅館 PC の感染によるパスワード・Cookie の窃取: 本来のリスクが最も高い経路なのに、現状は5フェーズすべてが弱以下。最優先の「突破を防ぐ」「気付く」「戻す」がどれも弱かなし。MFA を入れても、盗まれた Cookie の再利用は止まらない
- 公開 URL の「被害を限定」（最優先・現状 中）: 1つのセッションで約465日分の予約を読める。実行 SA は Firestore 全体を読める
- 「気付く」: ログイン成功の Slack 通知に偏っている。ログインの失敗、盗まれた Cookie の再利用、GCP の IAM の変更は見えない
- 「戻す」: Firestore の PITR・バックアップがない。管理者アカウントの乗っ取りの「戻す」は優先度 9（低）だが、現状がなしで、データを全部消されうる

### 脅威モデルに入っていないもの

- `gmail-listener`: 同じ Firestore に書き込む別リポジトリ。その実行 SA と予約メールの Gmail アカウントが §4 の入口にない。取られると、このアプリの防御を通らずに予約を読み書きできる
- Slack: ログインの通知（アカウント・IP）とエラーの文が集まる。Webhook の URL は環境変数（§8 後回し）
- 可用性・請求: 嫌がらせ目的の個人を想定しているが、§3 の守るものに入っていない
- ログアウトがなく、セッションを失効させる手順も文書にない（`verifySession` は `checkRevoked=true` なので、Firebase 側で失効させれば次の API から 401 になる）
