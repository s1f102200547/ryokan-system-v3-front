# Security Policy（脅威モデルと対策方針）

## 2. 判断の原則

- **リスク ＝ 起こりやすさ × 被害**。両方を見て順番を決める。
- 脆弱性は深刻度スコア（CVSS）だけで判断しない。「実際に悪用されているか（CISA KEV など）」と「このアプリで実行されうるコードか」で判断する。
- 脅威モデリングを用いる
- リスクへの対応は「低減・回避・移転・受容」の4択。受容したリスクは、理由と見直す条件を §8 に書く。

## 3. 前提（運用の実態）

- 利用する PC は約4台、スタッフは約10名。Firebase Auth のアカウントは **PC 単位**（人単位ではない）。
- 新規登録は無効。認可（ロール）は持たず、ログインできれば全機能を使える。
- ログインは Chrome / Edge のパスワードマネージャーの自動入力。パスワードは openssl で生成した。パスワードの変更機能はない。
- 本番は Cloud Run の `*.run.app` で、`.app` ドメインは全体が HTTPS強制する。利用できる時間は 6:00〜23:00 JST。
- PC の管理（OS、ブラウザ、メール）は旅館側の運用で、このアプリからは手を出せない。
- リポジトリは非公開。開発にはCloud codeを使う。

## 4. 守るもの

| 資産 | 場所 | 漏えい・改ざん・停止したときの被害 |
|---|---|---|
| 宿泊客の個人情報（氏名、国、メール本文のメモなど） | Firestore `guestInfoV2` | 宿泊客を狙う詐欺の材料になる。旅館の信用を失う。個人情報保護法にもとづく報告が必要になる(圧倒的最重要) |
| 宿泊税・金庫残高の記録 | `guestInfoV2`、`dailyInfo` | 改ざんされると会計が合わなくなる |
| 当日の業務（タイムテーブル、清掃ボード） | アプリ全体 | 止まると、当日の段取りに支障が出る |
| 本番環境の管理権限 | GitHub、GCP、Firebase | アプリの認証を通らずに全データを読まれる。改ざんしたコードをデプロイされる(重要) |

## 5. 入口（攻撃面）

```
[旅館の PC 4台] ──HTTPS──> [Cloud Run *.run.app（公開）] ──Admin SDK──> [Firestore]
      │
      └─(現状) パスワード ──> [Identity Toolkit（公開 API キーで誰でも呼べる）]

[開発 PC + AI エージェント] ──> [GitHub] ──CI / WIF──> [Artifact Registry] ──> [Cloud Run]
[npm レジストリ / GitHub Actions] ──> 開発 PC・CI・Docker build
```

| # | 入口 | 誰が到達できるか |
|---|---|---|
| E1 | Cloud Run の公開 URL | インターネット上の誰でも |
| E2 | Identity Toolkit（パスワードの判定） | API キーがブラウザ用のバンドルに入っているので、誰でも直接呼べる |
| E3 | Firestore | ブラウザからは使っていない。本番の Security Rules は全拒否（2026-11-01 確認）なので、ID トークンを持っていても直接は読めない。ただし Rules はサービスアカウント（サーバー側の権限）には効かない（T6） |
| E4 | 旅館の PC | スタッフ、ゲスト、PC に感染したマルウェア。保存されたパスワードと Cookie がある |
| E5 | GitHub・GCP・Firebase の管理者アカウント | アカウントを乗っ取った人 |
| E6 | 依存パッケージ、GitHub Actions | パッケージやアクションのメンテナ（乗っ取られた場合を含む） |
| E7 | Git リポジトリ（過去の履歴を含む） | リポジトリを読める人。GitHub アカウントを乗っ取った人。公開に切り替えた場合は誰でも |
| E8 | 開発者の PC | PC に入り込んだマルウェア、悪性のパッケージや拡張機能、AI エージェントに読ませた外部の文章（間接プロンプトインジェクション）。PC には GitHub に push できる SSH 鍵、ブラウザに残る GitHub・Google Cloud・Firebase コンソールのログイン状態、ソースコードがある。AI エージェントは開発者と同じ権限でコマンドを実行できる。gcloud の認証情報は `anonymize` の実行中だけ作り、終了時に削除している（2026-11-01 確認） |

## 6. 想定する攻撃者

| 型 | 実態 | 目的 |
|---|---|---|
| 無差別型のボット | 公開したサーバーは、すぐに自動スキャンを受ける。既知の脆弱性（React2Shell など）は、公表から間もなく大量に悪用される | 踏み台、暗号資産の採掘、データの窃取 |
| 宿泊業界を狙う犯罪グループ | Booking.com を装ったメールで偽の確認画面に誘導し、スタッフ自身にコマンドを実行させて（ClickFix）、情報を盗むマルウェアを入れる（Storm-1865、2024年12月〜）。予約管理システムへの不正アクセスのあと、予約者に偽のメッセージが送られた事例もある（TEMAIRAZU、2026年9月。最大約445万人が対象になる可能性。両者の関係は調査中と発表） | 予約データを使った、宿泊客への詐欺 |
| 開発者を狙う攻撃者（サプライチェーンを含む） | ① 情報を盗むマルウェアの配布者：偽のソフトや広告、ClickFix で一般の PC に感染させ、ブラウザのログイン状態（Cookie）や SSH 鍵を盗んで売る。② 開発者を狙うグループ：偽の求人で「課題」のリポジトリを VS Code で開かせ、`.vscode/tasks.json` などで自動的にマルウェアを実行させる（Contagious Interview、北朝鮮系）。③ npm のメンテナのアカウントを乗っ取り、悪性のバージョンを公開する（axios、2026年3月、北朝鮮系 UNC1069。Shai-Hulud） | 暗号資産と、売買できる認証情報。**旅館を狙っているわけではない**が、盗まれた認証情報の先に旅館の本番環境がある |
| 内部の人 | スタッフ（退職者を含む）やゲストが、旅館の PC に触れられる | パスワードを持ち帰り、外から使う |

**有名旅館であること**は、宿泊客が詐欺の標的として価値が高いことを意味する。

想定しない攻撃者:
- 国家レベルの攻撃者が、旅館を狙って仕掛けてくる攻撃（ゼロデイ脆弱性、ハードウェアへの攻撃）。上の北朝鮮系のように、開発者全般を無差別に狙う金銭目的の攻撃は想定する
- 大規模な DDoS（§8 で受容する）
- 盗んだ PC を解析すること（PC を紛失・盗難したら、その端末とアカウントを無効にして対応する）

## 7. 脅威と方針

| # | 脅威 | 入口 | 起こりやすさ | 被害 | 方針 |
|---|---|---|---|---|---|
| T1 | ボットによる総当たり | E1、E2 | 試行は高（常に来る）。成功は低（パスワードが強い） | 大（成功すれば全データ） | 低減 |
| T2 | ClickFix などで PC が感染し、パスワードや Cookie を盗まれる | E4 | 中 | 大 | 受容（一部を低減） |
| T3 | パスワードの盗み見・持ち出し | E4 | 低〜中 | 大 | 受容（端末登録で低減） |
| T4 | Session Cookie のコピー | E4 | 低 | 中（当日 23:00 まで） | 受容 |
| T5 | 開発者の PC・管理者アカウントの乗っ取り | E5、E8 | 低〜中 | 致命的 | 低減（最優先） |
| T6 | 既知の脆弱性・悪性パッケージの悪用 | E1、E6 | 高 | 致命的 | 低減（最優先） |
| T7 | ソースコードの欠陥（AI が生成したコードを含む） | E1 | 中 | 大 | 低減 |
| T8 | 機密情報・宿泊客の実データの混入 | E7 | 低〜中 | 大 | 低減 |

評価の根拠（2026-11-01 時点）:
- T1: パスワードは openssl で生成しているので、総当たりの成功はほぼない。ただし成功した場合の被害は全データなので、被害は「大」とする。
- T3: スタッフ専用の PC で、悪意をもって開発者ツールを使う内部の人は多くない。
- T4: Cookie は当日 23:00 で切れる。コピーできる内部の人は、PC の前にいれば元々すべてのデータを見られる。コピーで増えるのは「当日中に外から使える」ことだけ。
- T6: 自動スキャンは常に来る。被害の大きさは、修正版への更新の速さで決まる。
- T7: 未ログインの API 呼び出しが 401 になることは、全 Route を列挙するテストで機械的に確認済み。残るのは、入力の上限や情報の出しすぎなど。

具体的な対策は `docs/Security/SecurityMeasures/` に、脅威の番号ごとのファイル（`T1.md`〜`T8.md`）で書く。

### T1: ボットによる総当たり

**説明**: インターネットに公開されたログイン画面に、ボットがパスワードを大量に試す。今の構成では、パスワードの判定がブラウザから Google の Identity Toolkit に直接送られ、そのための API キーも公開されている（E2）。そのため攻撃者は**アプリを通らずに Google の窓口へ直接総当たりでき**、アプリ側に回数制限を作っても回り込まれる。一方で、パスワードは openssl で生成しているので、推測で当てることは現実的にできない。

**方針: 低減**
- パスワードを試す**裏口（E2）をなくす**。パスワードの試行は、すべてアプリのサーバーを通るようにする。
- 登録した PC 以外からは、**パスワードの判定まで到達させない**。
- 試行を**観察できる**ようにし、外からのログインに気付けるようにする。
- 特定の回数以上間違えたらx分後まで使えないみたいにしたい。

**残るリスク**: 登録済みの PC を使われる場合（T2、T3）。

### T2: ClickFix などで PC が感染し、パスワードや Cookie を盗まれる

**説明**: 犯罪グループが Booking.com を装ったメール（悪い口コミが付いた、予約の問い合わせ、など）で偽の CAPTCHA 画面に誘導し、「確認のため」と称してスタッフ自身にコマンドを貼り付けて実行させる。そうして PC にマルウェアを入れ、保存されたパスワードや Cookie を盗む。盗んだ予約データは、宿泊客への詐欺メッセージに使われる。

**方針: 受容する**（PC の管理は旅館側の運用で、アプリからは手を出せない）
- ただし、T1・T3 の対策（端末登録）で「盗んだパスワードを**外から使えない**」ようにして、被害を小さくする。

### T3: パスワードの盗み見・持ち出し

**説明**: スタッフやゲストが旅館の PC のブラウザを使い、保存されたパスワードを盗み見る。自動入力させてから開発者ツールで `type="text"` に書き換えれば、OS の認証なしでも平文が見える。盗んだパスワードは、自宅からでも退職後でも外から使える。

**方針: 受容する**（ブラウザの設定はアプリからは変えられない）
- ただし、**パスワードだけでは登録した PC 以外から使えない**ようにして、ほぼ防ぐ。

**残るリスク**: 開発者ツールで端末の証明（Cookie）まで意図的にコピーされる場合。T4 と同じ理由で受容する（§8）。

### T4: Session Cookie のコピー

**説明**: ログイン中の PC で開発者ツールを開くと、`session` Cookie が見える（`httpOnly` は JavaScript からの読み取りを防ぐだけ）。これをコピーすれば、別の PC でも 23:00 までログインした状態で使える。今の Cookie は「持っている人なら誰でも使える入館証」になっている。

**方針: 受容する**
- Cookie は当日 23:00 で切れるので、使われる期間は最大でも当日中に限られる。
- コピーできるのは、旅館の PC の前で開発者ツールを使える人だけ。その人は PC の前にいれば元々すべてのデータを見られるので、コピーで増える被害は「当日中に外から使える」ことに限られる。
- セッションの寿命（当日 23:00）は短いまま保つ。延ばす変更はしない。
- Cookie を PC のハードウェアに結び付ける対策（DBSC）は、効果に対して実装の負担が大きいので保留する（`SecurityMeasures/Rejected.md`）。

### T5: 開発者の PC・管理者アカウントの乗っ取り

**説明**: GitHub・GCP・Firebase のアカウントを乗っ取られると、**アプリの認証を通らずに** Firestore の全データを読まれたり、改ざんしたコードを本番にデプロイされたりする。アプリ側の対策では防げない、別の入口（E5）である。

開発者の PC（E8）が乗っ取られた場合も、同じところに行き着く。盗まれるものごとに、今の設定で何ができてしまうかを整理する（2026-11-01 時点の `.github/workflows/` と開発 PC で確認）。

| 盗まれるもの | 今の設定で、攻撃者にできてしまうこと |
|---|---|
| GitHub に push できる SSH 鍵 | ① `main` にブランチ保護がないので、`main` に直接 push すれば、CI を通って本番に自動でデプロイされる。② **`main` を通らない経路もある**。デプロイ用の secrets（WIF の provider、サービスアカウント、Slack の Webhook）は、Environment ではなく**リポジトリ全体の secrets** にある。そのため、適当なブランチに自作のワークフローを push すれば、そのワークフローから secrets をすべて読める。さらに `id-token: write` を付ければ GitHub の OIDC トークンを取得でき、WIF の条件が「このリポジトリなら誰でも」程度なら、デプロイ用のサービスアカウントになりすまして、Cloud Run に直接デプロイできる |
| ブラウザの GitHub のログイン状態（Cookie） | PR を作ってマージする、ブランチ保護や secrets の設定を変える。ログイン済みの状態をそのまま使われるので、**パスキーを登録していても素通りされる** |
| ブラウザの Google のログイン状態（Cookie） | 開発者のアカウントは GCP のオーナーなので、GCP と Firebase のすべてを操作できる（Firestore の全データの読み取り、Cloud Run の書き換え、ログの削除） |
| AI エージェントへの指示（間接プロンプトインジェクション） | 外部の文章（Web ページ、Issue、パッケージの README など）に仕込まれた指示に従い、開発者の権限で `git push` や任意のコマンドを実行する。`~/.ssh` の鍵も読める |
| 素性の分からないリポジトリを開く | VS Code で開いた瞬間に `.vscode/tasks.json` などからマルウェアが動き、上のすべてを盗まれる |

なお、gcloud の認証情報は `anonymize` の実行中だけ作り、終了時に削除している（確認済み）。GCP のサービスアカウントの鍵ファイルもない（WIF を使っている）。

**方針: 低減（最優先）。人の注意ではなく、仕組みで止める**
- **1つの認証情報が盗まれただけでは、本番に届かない**ようにする。push できる鍵、マージできる権限、GCP を操作できる権限を、それぞれ別の関所にする。
- 本番に入る経路を **`main` の `deploy.yml` だけ**に絞る。GitHub 側（ブランチ保護、Environment）と GCP 側（WIF の条件）の両方で絞り、片方が破られても止まるようにする。
- 強い権限（GCP のオーナー）は、**普段使うアカウントに持たせない**。開発 PC のブラウザが乗っ取られても、届く範囲を小さくする。
- AI エージェントの権限は、**設定で機械的に制限する**（push・デプロイ・鍵の読み取りをできなくする）。
- 仕組みで防ぎきれない部分（GitHub・Google のログイン状態の乗っ取り）は、**検知と復元**で被害を抑える（本番へのデプロイと GCP の管理操作を通知する。Firestore のバックアップを持つ）。

**残るリスク**: GitHub と Google の両方のログイン状態を同時に盗まれること。検知と復元で対応する。

### T6: 既知の脆弱性・悪性パッケージの悪用

自分が書いたコードではなく、**使っている部品（Next.js、React、npm のパッケージ）**から攻撃される脅威。経路は次の2つ。

**経路1：公開された脆弱性を突かれる（入口 E1）**

*実際に起きたこと*: React2Shell（CVE-2025-55182、2025年12月3日公表）。Next.js の App Router が使う React Server Components の通信データの読み取り処理に欠陥があった。**ログインしていなくても、細工した HTTP リクエストを1回送るだけで、サーバー上で好きなコマンドを実行できた**。公表の翌日には中国系の複数のグループが悪用を始め、侵入したサーバーからクラウドの認証情報を盗もうとした。このアプリも App Router を使っているので、修正前のバージョンなら対象だった（今の React 19.2.4 / Next.js 16.4.3 は修正済み）。

*このアプリで起きること*: Cloud Run のコンテナの中でコマンドを実行されると、次の順に被害が広がる。
1. 環境変数を読まれる（Slack の Webhook の URL）。
2. コンテナの中からは、Cloud Run に割り当てたサービスアカウントの権限をそのまま使える。その権限で Firestore を直接呼ばれ、**宿泊客の全データを読まれる**。**Security Rules はサービスアカウントには効かないので、全拒否にしていても防げない**。
3. そのサービスアカウントが既定の Compute Engine のもので、プロジェクト全体の Editor 権限を持っていた場合は、Cloud Run を書き換えてバックドアを仕込むなど、GCP のほぼすべてを操作される。今の deploy はサービスアカウントを指定していないので、この既定のアカウントで動いている可能性がある（要確認）。

つまり、この経路の**本当の防御は「修正版にすぐ更新すること」**である。権限を絞っても、被害を 3 から 2 に抑えられるだけで、2 は防げない。

なお、Next.js では 2026 年に「middleware / proxy の認証をすり抜ける」脆弱性が何度も出た。このアプリは、各 API で session を確認し、proxy を認証の境界にしていないので、影響を受けにくい（設計で防げた例）。

**経路2：悪性のパッケージを入れてしまう（入口 E6）**

*実際に起きたこと*: axios（2026年3月31日）。メンテナのアカウントが乗っ取られ、悪性のバージョン（1.14.1 と 0.30.4）が公開された。悪性版は依存に `plain-crypto-js` を追加しており、その install 時のスクリプト（postinstall）が、`npm install` した瞬間に遠隔操作のマルウェアを入れた。悪性版は数時間で削除されたが、その間に install した PC や CI は感染した。

*このアプリで install が動く場所と、盗まれうるもの*:

| 場所 | いつ動くか | 盗まれうるもの |
|---|---|---|
| 開発者の PC | `npm install` / `npm ci` を実行したとき | GitHub に push できる SSH 鍵、ブラウザのログイン状態（→ T5） |
| CI（GitHub Actions） | lock ファイルが変わり、キャッシュが使えないとき | ジョブに渡された権限（今はワークフロー全体に `issues: write`） |
| deploy の Docker build | デプロイのたび | build は、GCP にログインした状態のジョブの中で動く。`google-github-actions/auth` が作る認証ファイル（`gha-creds-*.json`）は、`.dockerignore` で除外していないので、`COPY . .` で build の中に入るおそれがある（要確認） |

install 時のスクリプトを止めても、悪性のコードがパッケージの本体にあれば、build・テスト・本番の実行時に動く。そのため「公開されたばかりのバージョンを入れない」ことが重要になる。axios の悪性版のように、多くは数時間〜数日で見つかって削除されるので、**数日待つだけで大半を避けられる**。

**方針: 低減（最優先）**
- 悪用が報告された脆弱性は、**数日以内に修正版をデプロイ**する。経路1の本当の防御はこれしかない。
- 乗っ取られたときに備えて、Cloud Run のサービスアカウントの権限を **Firestore と Firebase Auth に必要な分だけ**にする（Editor を持たせない）。
- 依存は**公開から数日たったバージョンだけ**を入れる。install 時のスクリプトは実行しない。lock ファイルどおりに入れる。
- CI と Docker build の中に、**盗まれて困る認証情報を置かない**。

### T7: ソースコードの欠陥（AI が生成したコードを含む）

**説明**: 自分、または AI のコーディング支援が書いたコードに脆弱性が入る。このアプリで特に起こりやすく、被害が大きいのは次の3つ。
- 新しい API で、session の確認（`requireSession`）を忘れる（A01）
- 入力の長さや件数に上限がない
- エラーのレスポンスやログ、Slack に内部の情報や個人情報を出す

**方針: 低減**
- 人の注意に頼らず、**機械で止める**（テスト、静的解析）。機械で見つけられない設計上の欠陥は、この文書の脅威の整理とレビューで見る。

### T8: 機密情報・宿泊客の実データの混入

**説明**: API キーや Webhook の URL、**宿泊客の実データ**を Git に入れて push してしまう。一度 push すると履歴に残り続け、リポジトリを読める人全員に見える。今は本物の秘密情報をほとんど持っていない（GCP は WIF で鍵ファイルがなく、開発環境は Emulator だけ）が、ログインのサーバー経由化（T1）でサーバー専用の API キーが増える。また、秘密情報の検査ツールでは**個人情報は見つけられない**。

**方針: 低減**
- **秘密情報そのものを持たない**ことを第一にする。持つものは、シークレット管理（Secret Manager、GitHub Secrets）にだけ置く。
- 実データは**開発の場に持ち込まない**。テストデータは匿名化・生成したものだけを使う。
- 漏れたら、**履歴から消すより先にキーを無効化する**。
- リポジトリを公開する前に、全履歴を検査する。

| T2: PC の感染 | PC の管理は旅館側の運用で、アプリからは手を出せない | PC の管理方法が変わったとき。宿泊業界で同じ手口の被害が増えたとき |
