# 検討して採用しなかった・保留した対策

| 対策 | 判断 | 理由 | 見直す条件 |
|---|---|---|---|
| ログアウトボタン | 採用しない | スタッフ専用の PC で使う。緊急時はアカウントを無効にすれば、セッションも失効する（`IncidentResponse.md`） | 不特定の人が触れる場所に PC を置くとき |
| IAP（Google アカウントによる前段の認証） | 保留 | Edge でも使う。スタッフ用の Google アカウントの運用が必要になる | 端末登録が運用に合わないとき。スタッフごとのアカウントを作るとき |
| 異常時のアカウント自動無効化 | 保留 | 端末登録で未登録の端末を拒否できるので、追加の効果が小さい | 端末登録のあとも、不審なログインが観察されたとき |
| Trusted Types | 保留 | React が自動でエスケープし、`dangerouslySetInnerHTML` も使っていないので効果が小さい。Next.js / MUI / Firebase が動かなくなるおそれがある | HTML を直接扱う機能を追加するとき。試すときは Report-Only から始める |
| CodeQL、GitHub の Push Protection | 採用しない | 非公開リポジトリでは有料。Semgrep と gitleaks で代わりにする | リポジトリを公開するとき（どちらも無料になる） |
| `eslint-plugin-security` | 採用しない | TypeScript では誤検知が多く、Semgrep と役割が重なる | Semgrep で足りない検査が出てきたとき |
| gitleaks を commit 前のフックでも動かす | 任意 | CI で止められる。非公開リポジトリなので、push から CI までの間に読まれるおそれは小さい。フックのために npm の依存（husky など）を増やしたくない | 開発者が増えたとき。リポジトリを公開するとき |
| gitleaks に、個人情報を見つけるための独自ルールを入れる | 採用しない | 氏名などはパターンで見つけられず、テストデータで誤検知が増える。実データの混入はルール（T8-2）とレビューで防ぐ | 予約番号など、形式が決まっている実データを扱うとき |
| DBSC（Cookie を PC のハードウェアに結び付ける） | 保留 | T4 を受容したため。Cookie を数分ごとに更新する仕組みをサーバーに作る必要があり、効果に対して負担が大きい。対応しているのは Windows 版の Chrome（146 以降）だけで、Edge の対応状況は要確認 | セッションの期限を延ばすとき。内部の人による不正が実際に起きたとき |
| Environment `production` の必須レビュアー（デプロイ前の承認） | 採用しない | 1人で開発しているので、自分で承認するだけになり、仕組みとしての効果がない。GitHub のログイン状態を盗まれた場合は承認もされてしまう | 開発者が2人以上になったとき |
| Binary Authorization（署名したイメージだけをデプロイさせる） | 採用しない | 設定と運用の負担が大きい。デプロイの経路は T5-1〜4 で `main` の `deploy.yml` に絞れる | 手作業のデプロイが必要になったとき |
| HSTS preload | 不要 | `*.run.app` は `.app` ドメインごと preload 済み | 独自ドメインに移るとき |
| Firebase のパスワードポリシー（最小文字数・Require モード） | 採用しない | パスワードは開発者が openssl で生成して設定し、スタッフが変更する機能もない。ポリシーは利用者がパスワードを決める場面で効くもので、この運用では効果がない | スタッフがパスワードを変更・設定できる機能を作るとき |
| パスワード強度の判定ライブラリ（`@zxcvbn-ts/core` など） | 採用しない | パスワードを決めるときに弱いものをはじく道具で、ログイン時の確認には要らない。辞書データで依存とバンドルが大きくなる。ログイン時は、すでにある Zod で長さを確認すれば足りる（T1-5） | 同上 |
| MFA | 不要（`docs/Security/SecurityPolicy.md` §8） | 端末登録で代わりにする | `docs/Security/SecurityPolicy.md` §8 のとおり |
