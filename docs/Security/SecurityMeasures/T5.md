# T5: 開発者の PC・管理者アカウントの乗っ取り

脅威の説明と方針は `docs/Security/SecurityPolicy.md` の T5 を参照。方針は「1つの認証情報が盗まれただけでは本番に届かないように、仕組みで止める」。

## すでに効いている対策

- GCP の認証は WIF で、サービスアカウントの鍵ファイルがない。
- gcloud の認証情報は `anonymize.sh` の実行中だけ作り、終了時に削除している（開発 PC に残っていないことを 2026-11-01 に確認）。
- 開発環境は Emulator にだけつながり、本番の認証情報を置けない（`runtimeEnvGuard`）。AI エージェントが開発環境の設定を読んでも、本番には届かない。

## 盗まれるものと、止める仕組み

| 盗まれるもの | 止める仕組み（下の対策の番号） |
|---|---|
| SSH 鍵 | `main` への直接 push を禁止（1）。ブランチに自作のワークフローを push されても、secrets を読めず（2）、GCP にも入れない（3） |
| GitHub のログイン状態 | 仕組みでは防ぎきれない。本番へのデプロイを通知して気付く（9） |
| Google のログイン状態 | 普段使うアカウントにオーナー権限を持たせない（5） |
| AI エージェントへの指示 | エージェントの権限を設定で制限する（7） |
| 素性の分からないリポジトリ | 信頼していないフォルダーでは、自動実行させない（8） |

## 対策

| 順番 | 内容 | 段階 |
|---|---|---|
| 1 | **`main` をルールセットで保護する**。PR を必須にし、CI の全ジョブ（Lint、Type Check、npm audit、Unit Test、Emulator Round-trip Test、E2E Test）の合格を必須にする。force push と削除を禁止する。バイパスできる人は設定しない（管理者も PR を通す）。1人で開発しているので、承認の人数は 0 でよい。**SSH 鍵は push しかできないので、PR のマージ（GitHub のログインが必要）と分けられる**。`development` にも同じ保護（CI の合格と force push の禁止）を付ける | P0 |
| 2 | **デプロイ用の secrets を Environment `production` に移す**。Environment の「Deployment branches」を `main` だけにする。`deploy.yml` の deploy ジョブに `environment: production` を付ける。移す secrets: `WORKLOAD_IDENTITY_PROVIDER`、`SERVICE_ACCOUNT`、`GCP_PROJECT_ID`、`SLACK_WEBHOOK_URL`（Secret Manager に移すまで。T8-4）。移したあとは、リポジトリ全体の secrets から削除する。**ほかのブランチのワークフローからは読めなくなる** | P1 |
| 3 | **WIF の provider の条件で、GCP に入れるワークフローを絞る**。属性の対応付け（attribute mapping）に `assertion.repository`、`assertion.ref`、`assertion.workflow_ref` を追加し、条件を次のようにする。`assertion.repository == '<owner>/<repo>' && assertion.ref == 'refs/heads/main' && assertion.workflow_ref.startsWith('<owner>/<repo>/.github/workflows/deploy.yml@')`。2 のあとに `assertion.environment == 'production'` も加える。**GitHub 側（1・2）が破られても、GCP 側で止まる**。大文字・小文字は区別されるので、実際のトークンの値に合わせる。今の条件が何になっているかは要確認 | P0 |
| 4 | **デプロイ用のサービスアカウントの権限を、対象のリソースだけに付ける**。Cloud Run のサービス `ryokan-system` に `roles/run.developer`、実行用のサービスアカウント（T6-1）に `roles/iam.serviceAccountUser`、Artifact Registry のリポジトリ `ryokan` に `roles/artifactregistry.writer`。プロジェクト全体には権限を付けない | P0 |
| 5 | **普段使う Google アカウントから、GCP のオーナー権限を外す**。普段のアカウントには、日常の作業に必要な閲覧系の権限（ログ、Cloud Run、Firestore の閲覧など）だけを付ける。オーナーは別のアカウントに持たせ、必要なときだけ別のブラウザのプロファイルでログインする。**開発 PC のブラウザが乗っ取られても、GCP 全体には届かない** | P0 |
| 6 | GitHub と Google の両方のアカウント（5 のオーナー用も含む）に**パスキー**を登録する。パスキーはフィッシングに強いが、ログイン済みの状態（Cookie）を盗まれると効かないので、1〜5 と組み合わせる | P0 |
| 7 | **AI エージェントの権限を設定で制限する**。リポジトリに `.claude/settings.json` を置き、`permissions.deny` に `Bash(git push:*)`、`Bash(gcloud:*)`、`Bash(firebase deploy:*)`、`Read(~/.ssh/**)`、`Read(~/.config/gcloud/**)` を入れる。push とデプロイは人が行う。サンドボックス（コマンドのファイル・ネットワークへのアクセスを制限する機能）が WSL で使えるかは要確認。Codex を使う場合は、同じ制限を Codex の設定にも入れる | P1 |
| 8 | **開発 PC の設定**：VS Code の Workspace Trust を有効のまま使う（信頼していないフォルダーでは `tasks.json` などが自動で実行されない）。素性の分からないリポジトリ（求人の課題など）は、Dev Container や Codespaces など別の環境で開く。SSH 鍵にパスフレーズを付ける | P0 |
| 9 | **本番へのデプロイを通知する**。Slack の GitHub アプリで `Deploy to Cloud Run` のワークフローの開始と結果を通知する（`workflows` の購読）。身に覚えのないデプロイに気付ける。`deploy.yml` の中で通知しないので、ワークフローを書き換えられても通知は止まらない（2026-11-02 に `deploy.yml` の Webhook の通知から切り替えた） | P1 |
| 10 | 秘密情報の検査は **T8-1 の gitleaks で行う**。GitHub の Secret scanning と Push protection は、個人アカウントの非公開リポジトリでは使えない（設定画面の Push protection の説明が「public repositories」だけを対象にしている。2026-11-01 確認）。GitHub Pro にしたら、使えるようになるかを確かめる | P1 |
| 11 | **乗っ取られても戻せるようにする**。Firestore の PITR（過去の時点への復元）と削除保護、定期バックアップを有効にする | P1 |

## 確認方法

- 1: ルールセットを作ったあと、`main` に直接 push して拒否されることを確かめる。
- 2・3: 適当なブランチに、`id-token: write` と `google-github-actions/auth` を使う確認用のワークフローを push し、GCP の認証が失敗することを確かめる（確かめたらブランチを削除する）。
- 7: エージェントに `git push` を頼み、拒否されることを確かめる。
