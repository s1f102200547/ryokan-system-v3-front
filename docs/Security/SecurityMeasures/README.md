# Security Measures（セキュリティ対策と実施計画）

`docs/Security/SecurityPolicy.md` の脅威（T1〜T8）と方針にもとづく、具体的な対策をまとめる。

- 各対策には、効く脅威を書く。どの脅威にも効かない対策は入れない。
- 対策が終わったら、今の実装の説明を `docs/Security/Security.md` に移し、対策のファイルの該当箇所は「済」にする。

## ファイル一覧

| ファイル | 内容 |
|---|---|
| `T1.md`〜`T8.md` | 脅威ごとの対策（`T1-2` のように「脅威の番号-対策の順番」で参照する） |
| `ImplementationPlan.md` | 実施計画（P0〜P4）を作業のステップに分けたもの。Claude が編集する部分と、開発者が手で設定・確認する部分に分ける |
| `Rejected.md` | 検討して採用しなかった・保留した対策 |

## 実施計画

| 段階 | 内容 | 効く脅威 | 種類 |
|---|---|---|---|
| P0 | T5 の P0 の項目（ブランチ保護、WIF の条件、デプロイ用サービスアカウントの権限、オーナー権限の分離、パスキー、開発 PC の設定、Secret scanning）、新規登録が API レベルで無効かの確認、予算アラート | T5、T1 | 設定 |
| P1 | T6-1〜10、T5 の P1 の項目（Environment、AI エージェントの制限、デプロイの通知、バックアップ）、T7-1〜5、T8-1〜3、T1-1（IP 通知で観察を始める） | T1、T5、T6、T7、T8 | コードと設定 |
| P2 | 端末登録（T1-2） | T1、T3、T2（一部） | コード |
| P3 | ログインのサーバー経由化、失敗回数の制限、パスワードの事前チェック（T1-3〜5。`firebase` パッケージの削除、API キーの作り直し、CSP と audit 例外の整理を含む） | T1 | コード |
| P4 | Terraform による設定のコード化と、ずれの自動検知。P1 が終わったあとなら、いつ始めてもよい | T5、T6 | コード |

**順番の理由**

- **P0・P1 を最初に行う**。T5 と T6 は被害が致命的で、多くは設定の変更か小さなコード変更で済む。特に T5-1〜3（ブランチ保護、Environment、WIF の条件）は、SSH 鍵1つで本番に届く今の経路を塞ぐので最優先。
- **P2（端末登録）を P3（サーバー経由化）より先に行う**。端末登録は、セッション Cookie を発行する関所（`/api/auth/login`）で確認するので、サーバー経由化しなくても効く（本番の Firestore Rules は全拒否なので、ID トークンだけでは何もできない）。端末登録は T1・T2・T3 にまとめて効く。サーバー経由化の主な効果は「パスワード試行の回数制限」で、強いパスワードを使っている今は効果が比較的小さい。
- 実装は AGENTS.md の実装方針（E2E → domain の unit test → …）に沿って進める。

**進め方**

- 設計（端末登録のスキーマ、登録コードの発行方法など）は、着手するときに該当する `Tx.md` に追記する。
- CI/CD を変更するときは、AGENTS.md のとおり `docs/CICD.md` も同時に更新する。
