# T1: ボットによる総当たり

脅威の説明と方針は `docs/Security/SecurityPolicy.md` の T1 を参照。

## 対策

| 順番 | 内容 |
|---|---|
| 1 | **ログインに成功したときの接続元 IP を Slack に通知する**。数週間観察し、旅館の IP が固定なら IP 制限を検討する（未着手。Step 1-11） |
| 2 | **端末登録**（T3 と共通）。登録した端末の Cookie がなければ、パスワードを見る前に拒否する。**旅館側の作業や連絡なしで完結させる**（下の「端末登録の進め方」）（未着手。P2） |
| 3 | **ログインをサーバー経由にする**。ブラウザはアプリのログイン API にだけ送り、Google への問い合わせはサーバーが行う。API キーは作り直してサーバー専用にし（Secret Manager）、古いキーは削除する（裏口をなくす）（未着手。P3） |
| 4 | **失敗回数の制限**。アカウントごと・端末ごとに連続5回まで。超えたら15分待たせ、繰り返すたびに待ち時間を延ばす。IP ごとに1時間で20回を超えたら Slack に通知する（未着手。P3） |
| 5 | **パスワードの形式チェック**。ログイン API の入力検証（Zod）で長さを確認し、範囲外なら Google に問い合わせずに拒否する。(10~100)。メッセージは通常の失敗と同じにする。新しいライブラリは使わない（`Rejected.md`）（未着手。P3） |

## 端末登録の進め方

期限切れのたびに登録し直したり、旅館側に作業を頼んだりしなくて済むようにする。

| 場面 | 動き |
|---|---|
| 最初の登録 | 機能を入れたあと、各アカウントで最初にログインしたブラウザに端末 Cookie を発行し、そのアカウントの端末として Firestore に登録する（初回利用時の自動登録）。アカウントは PC 単位なので、スタッフはいつもどおりログインするだけでよい |
| 有効期限 | 端末 Cookie は、ログインのたびに有効期限を延ばす（ブラウザの上限は約400日）。毎日使う PC では、実際には切れない |
| ブラウザを追加した・データを消した | 登録済みの端末が最近（例: 7日以内）ログインしたのと**同じ IP から**なら、新しいブラウザも自動で登録する（Chrome と Edge の併用や、Cookie の消失に対応する）。登録したら Slack に通知する |
| 違う IP の未登録のブラウザ | 拒否し、IP を付けて Slack に通知する |
| 端末の取り消し | 開発者が Firestore の登録を消す（PC の紛失時など）。旅館側の作業は要らない |

限界:
- 機能を入れた直後に、スタッフより先に攻撃者がログインすると、攻撃者の端末が登録される（その時点でパスワードが漏れていた場合だけ）。登録の通知で気付ける。
- 旅館のネットワーク（同じ IP）の中からなら、パスワードを知っている人は自分の端末を登録できる。ゲストが同じ回線を使う場合は、T3 の盗み見に対して効果が弱まる。登録の通知で気付けるようにし、スタッフ用とゲスト用の回線が分かれているかを確認する（要確認）。
- 旅館の IP が頻繁に変わる場合は、「同じ IP からの自動登録」が効きにくい。T1-1 の観察結果で判断する。

## 設計上の注意

- 判定の順番は **端末の確認 → 回数制限 → パスワードの判定** にする。こうすれば、端末を持たない攻撃者はアカウントをロックさせることもできない（スタッフを締め出す DoS を防ぐ）。
- 回数のカウンターは Firestore に置く。Cloud Run は複数のインスタンスで動くので、メモリ上のカウンターは効かない。
- サーバー経由にすると、パスワードがサーバーを通る。request body をログや Slack に出さない。
- サーバー経由にすれば、ブラウザ用の `firebase` パッケージは不要になる。そのとき CSP の `connect-src` から Identity Toolkit を外し、npm audit の例外（grpc-js）も削除する。
