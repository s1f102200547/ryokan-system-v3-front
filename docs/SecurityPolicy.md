# Security Policy（脅威にもとづく対策方針）

## 1. この文書の位置づけ

- `docs/Security.md` は、今の実装（ヘッダー、CSP、Cookie、認証フロー）を説明する。
- この文書は、**何を・誰から・どこで守るか**（脅威モデル）と、対策の優先順位、受容したリスク、実施計画を決める。
- 対策を追加・変更するときは、§7 のどの脅威に効くかを先に書く。どの脅威にも効かない対策は入れない。

## 2. 判断の原則

- **リスク ＝ 起こりやすさ × 被害**。両方を見て順番を決める。
- 脆弱性は深刻度スコア（CVSS）だけで判断しない。「実際に悪用されているか（CISA KEV など）」と「このアプリで実行されるコードか」で判断する（例: `scripts/ci/auditAllowlist.ts`）。
- 脅威モデリングの4つの質問で考える。何を作っているか（§3〜§5）→ 何がまずいことになり得るか（§6〜§7）→ どうするか（§7、§9、§10）→ 十分か（§8、§11）。
- **攻撃者に合わせる**。実際に来る攻撃者（§6）に効く対策を選び、想定しない攻撃者のための重い対策はしない。
- **使いにくい対策は守られない**。スタッフの操作（パスワードの自動入力 → ボタンを押す）を変えない範囲で設計する。
- 仕組みは単純にする。暗号や認証は自作せず、Firebase・GCP・ブラウザの標準機能を使う。
- リスクへの対応は「低減・回避・移転・受容」の4択。受容したリスクは、理由と見直す条件を §8 に書く。

## 3. 前提（運用の実態）

- 利用する PC は4台、スタッフは約10名。Firebase Auth のアカウントは **PC 単位**（人単位ではない）。
- 新規登録は無効。認可（ロール）は持たず、ログインできれば全機能を使える。
- ログインは Chrome / Edge のパスワードマネージャーの自動入力。パスワードは openssl で生成した。パスワードの変更機能はない。
- 本番は Cloud Run の `*.run.app` で、`.app` ドメインは全体が HSTS preload 済み。利用できる時間は 6:00〜23:00 JST。
- PC の管理（OS、ブラウザ、メール）は旅館側の運用で、このアプリからは手を出せない。

## 4. 守るもの

| 資産 | 場所 | 漏えい・改ざん・停止したときの被害 |
|---|---|---|
| 宿泊客の個人情報（氏名、国、メール本文のメモなど） | Firestore `guestInfoV2` | 宿泊客を狙う詐欺の材料になる。旅館の信用を失う。個人情報保護法にもとづく報告が必要になる |
| 宿泊税・金庫残高の記録 | `guestInfoV2`、`dailyInfo` | 改ざんされると会計が合わなくなる |
| 当日の業務（タイムテーブル、清掃ボード） | アプリ全体 | 止まると、当日の段取りに支障が出る |
| 本番環境の管理権限 | GitHub、GCP、Firebase | アプリの認証を通らずに全データを読まれる。改ざんしたコードをデプロイされる |

## 5. 入口（攻撃面）

```
[旅館の PC 4台] ──HTTPS──> [Cloud Run *.run.app（公開）] ──Admin SDK──> [Firestore]
      │
      └─(現状) パスワード ──> [Identity Toolkit（公開 API キーで誰でも呼べる）]

[開発 PC + AI エージェント] ──> [GitHub] ──CI / WIF──> [Artifact Registry] ──> [Cloud Run]
[npm レジストリ / GitHub Actions] ──> 開発 PC・CI・Docker build
```

| # | 入口 | 誰が到達できるか |
|---|---|---|
| E1 | Cloud Run の公開 URL | インターネット上の誰でも |
| E2 | Identity Toolkit（パスワードの判定） | API キーがブラウザ用のバンドルに入っているので、誰でも直接呼べる |
| E3 | Firestore | ブラウザからは使っていないが、Security Rules 次第では ID トークンで直接読める |
| E4 | 旅館の PC | スタッフ、ゲスト、PC に感染したマルウェア。保存されたパスワードと Cookie がある |
| E5 | GitHub・GCP・Firebase の管理者アカウント | アカウントを乗っ取った人 |
| E6 | 依存パッケージ、GitHub Actions | パッケージやアクションのメンテナ（乗っ取られた場合を含む） |

## 6. 想定する攻撃者

| 型 | 実態 | 目的 |
|---|---|---|
| 無差別型のボット | 公開したサーバーは、すぐに自動スキャンを受ける。既知の脆弱性（React2Shell など）は、公表から間もなく大量に悪用される | 踏み台、暗号資産の採掘、データの窃取 |
| 宿泊業界を狙う犯罪グループ | Booking.com を装ったメールで偽の確認画面に誘導し、スタッフ自身にコマンドを実行させて（ClickFix）、情報を盗むマルウェアを入れる（Storm-1865、2024年12月〜）。予約管理システムへの不正アクセスのあと、予約者に偽のメッセージが送られた事例もある（TEMAIRAZU、2026年9月。最大約445万人が対象になる可能性。両者の関係は調査中と発表） | 予約データを使った、宿泊客への詐欺 |
| サプライチェーン攻撃者 | npm のメンテナのアカウントを乗っ取り、悪性のバージョンを公開する（axios、2026年3月。Shai-Hulud） | 開発 PC と CI の認証情報 |
| 内部の人 | スタッフ（退職者を含む）やゲストが、旅館の PC に触れられる | パスワードを持ち帰り、外から使う |

**有名旅館であること**は、宿泊客が詐欺の標的として価値が高いことを意味する。

想定しない攻撃者:
- 国家レベルの攻撃者（ゼロデイ脆弱性、ハードウェアへの攻撃）
- 大規模な DDoS（§8 で受容する）
- 盗んだ PC を解析すること（PC を紛失・盗難したら、その端末とアカウントを無効にして対応する）

## 7. 脅威と方針

| # | 脅威 | 入口 | 起こりやすさ | 被害 | 方針 |
|---|---|---|---|---|---|
| T1 | ボットによる総当たり | E1、E2 | 高（常に来る） | 中（パスワードが強いので成功しにくい） | 低減 |
| T2 | ClickFix などで PC が感染し、パスワードや Cookie を盗まれる | E4 | 中 | 大 | 受容（一部を低減） |
| T3 | パスワードの盗み見・持ち出し | E4 | 中 | 大 | 受容（端末登録で低減） |
| T4 | Session Cookie のコピー | E4 | 低〜中 | 大 | 低減（端末登録。将来は DBSC） |
| T5 | 開発者・管理者アカウントの乗っ取り | E5 | 低〜中 | 致命的 | 低減（最優先） |
| T6 | 既知の脆弱性・悪性パッケージの悪用 | E1、E6 | 高 | 致命的 | 低減（最優先） |

### T1: ボットによる総当たり

**説明**

インターネットに公開されたログイン画面に、ボットがパスワードを大量に試す。今の構成では、パスワードの判定がブラウザから Google の Identity Toolkit に直接送られ、そのための API キーも公開されている（E2）。そのため攻撃者は**アプリを通らずに Google の窓口へ直接総当たりでき**、アプリ側に回数制限を作っても回り込まれる。

一方で、パスワードは openssl で生成しているので、推測で当てることは現実的にできない。この脅威の対策は「パスワードを試す裏口をなくし、試行を観察できるようにする」ことに意味がある。

**対策**

| 順番 | 内容 |
|---|---|
| 1 | **ログインに成功したときの接続元 IP を Slack に通知する**。数週間観察し、旅館の IP が固定なら IP 制限を検討する |
| 2 | **端末登録**（T3 と共通）。登録した4台の PC の端末 Cookie がなければ、パスワードを見る前に拒否する |
| 3 | **ログインをサーバー経由にする**。ブラウザはアプリのログイン API にだけ送り、Google への問い合わせはサーバーが行う。API キーは作り直してサーバー専用にし（Secret Manager）、古いキーは削除する（裏口をなくす） |
| 4 | **失敗回数の制限**。アカウントごと・端末ごとに連続5回まで。超えたら15分待たせ、繰り返すたびに待ち時間を延ばす。IP ごとに1時間で20回を超えたら Slack に通知する |
| 5 | **パスワードの事前チェック**。15文字未満なら、Google に問い合わせる前に拒否する。メッセージは通常の失敗と同じにする |
| 6 | **Firebase のパスワードポリシー**。最小15文字・Require モードにする。先にスタッフ全員のパスワードを20文字のランダムなものに作り直す（Identity Platform の機能。使えるかは要確認） |

**設計上の注意**

- 判定の順番は **端末の確認 → 回数制限 → パスワードの判定** にする。こうすれば、端末を持たない攻撃者はアカウントをロックさせることもできない（スタッフを締め出す DoS を防ぐ）。
- 回数のカウンターは Firestore に置く。Cloud Run は複数のインスタンスで動くので、メモリ上のカウンターは効かない。
- サーバー経由にすると、パスワードがサーバーを通る。request body をログや Slack に出さない。
- サーバー経由にすれば、ブラウザ用の `firebase` パッケージは不要になる。そのとき CSP の `connect-src` から Identity Toolkit を外し、npm audit の例外（grpc-js）も削除する。

**残るリスク**: 登録済みの PC を使われる場合（T2、T3）。

### T2: ClickFix などで PC が感染し、パスワードや Cookie を盗まれる

**説明**

犯罪グループが Booking.com を装ったメール（悪い口コミが付いた、予約の問い合わせ、など）で偽の CAPTCHA 画面に誘導し、「確認のため」と称してスタッフ自身にコマンドを貼り付けて実行させる。そうして PC にマルウェアを入れ、保存されたパスワードや Cookie を盗む。盗んだ予約データは、宿泊客への詐欺メッセージに使われる。

**方針: 受容する**（PC の管理は旅館側の運用で、アプリからは手を出せない）

- 端末登録を入れれば、**パスワードだけを盗まれた場合は外から使えない**。Cookie まで盗まれた場合は、DBSC で補う（T4）。
- 外からのログインは、T1 の IP 通知で気付ける。
- （任意）スタッフに1行だけ周知する：「Web ページが『何かを貼り付けて実行して』と言ってきたら、100% 攻撃」。

### T3: パスワードの盗み見・持ち出し

**説明**

スタッフやゲストが旅館の PC のブラウザを使い、保存されたパスワードを盗み見る。自動入力させてから開発者ツールで `type="text"` に書き換えれば、OS の認証なしでも平文が見える。盗んだパスワードは、自宅からでも退職後でも外から使える。

**方針: 受容する**（ブラウザの設定はアプリからは変えられない）

- **端末登録で、ほぼ防げる**。パスワードを持ち帰っても、登録していない PC ではログインできない。
- 限界: 開発者ツールで**端末 Cookie まで意図的にコピー**されると、端末登録も破られる。これは DBSC で塞ぐ（T4）。

### T4: Session Cookie のコピー

**説明**

ログイン中の PC で開発者ツールを開くと、`session` Cookie が見える（`httpOnly` は JavaScript からの読み取りを防ぐだけ）。これをコピーすれば、別の PC でも 23:00 までログインした状態で使える。今の Cookie は「持っている人なら誰でも使える入館証」になっている。

**対策**

- 今の設計で効いている点: セッションは当日 23:00 で切れる。`HttpOnly` と `SameSite=Strict` を付けている。紛失時は、Firebase でアカウントを無効にすれば次の API 呼び出しから 401 になる（`verifySessionCookie(cookie, true)` で毎回失効を確認しているため）。
- 端末登録で、端末 Cookie のない PC からはログインできなくする。ただし、セッション Cookie そのものをコピーされた場合は防げない。
- 将来（余力があれば）**DBSC（Device Bound Session Credentials）** を入れる。Cookie を数分で切れる短命のものにし、更新のたびに PC のセキュリティチップ（TPM）の鍵で証明させる。コピーされた Cookie は数分で使えなくなる。端末 Cookie にも適用すれば、本当にその PC でなければ使えなくなる。
- 限界: 感染した PC の上で、その場で悪用されることは防げない。DBSC に対応しているのは Windows 版の Chrome（146 以降）で、Edge の対応状況は要確認。

### T5: 開発者・管理者アカウントの乗っ取り

**説明**

GitHub・GCP・Firebase のアカウントを乗っ取られると、**アプリの認証を通らずに** Firestore の全データを読まれたり、改ざんしたコードを本番にデプロイされたりする。アプリ側の対策では防げない、別の入口（E5）である。開発 PC でマルウェア（T6）や AI エージェントの誤操作が起きた場合も、ここに行き着く。

**対策**

| 順番 | 内容 |
|---|---|
| 1 | GitHub と Google アカウント（GCP・Firebase のオーナー）に**パスキー**を登録する |
| 2 | GCP の IAM で、本番を操作できるのが**自分とデプロイ用のサービスアカウントだけ**か確認する。サービスアカウントの鍵ファイルを発行していないことも確認する |
| 3 | Workload Identity Federation の provider に `attribute_condition` を付け、**このリポジトリの main だけ**が GCP に入れるようにする |
| 4 | GitHub の `main` と `development` をルールセットで保護する（PR を必須、CI の合格を必須、force push を禁止）。デプロイ用の secrets は Environment `production`（main だけが使える）に移す |
| 5 | Secret scanning と push protection を有効にする |
| 6 | AI エージェントには本番の認証情報を渡さない（`runtimeEnvGuard` で担保済み）。生成されたコードは CI とレビューを通す |
| 7 | 被害を小さくするため、Firestore の PITR（過去の時点への復元）と削除保護を有効にする |

### T6: 既知の脆弱性・悪性パッケージの悪用

**説明**

- **フレームワークの脆弱性**: React2Shell（CVE-2025-55182、RSC のデシリアライズによる RCE）は、公表直後から大量に悪用された。Next.js でも 2026 年に、middleware / proxy の認証をすり抜ける脆弱性が何度も出た（このアプリは proxy を認証の境界にしていないので、影響を受けにくい）。
- **悪性パッケージ**: 乗っ取られたバージョンの postinstall スクリプトは、開発 PC・CI・Docker build の `npm ci` で実行される。
- **被害が広がる経路**: Cloud Run で RCE を起こされると、そのサービスアカウントの権限で GCP を操作される。既定の Compute Engine サービスアカウントにはプロジェクト全体の Editor が付いていることがあり、その場合は全データと全リソースが対象になる。

**対策**

| 順番 | 内容 |
|---|---|
| 1 | Cloud Run を**専用のサービスアカウント**（Firestore と Firebase Auth に必要な権限だけ）で動かす。被害の範囲を小さくする |
| 2 | Firestore Security Rules を**全拒否**にする（`firestore.rules` で管理し、Emulator でテストする）。サーバーは Admin SDK を使うので影響しない。E3 を塞ぎ、T1〜T4 の端末登録を回り込めないようにする前提でもある |
| 3 | **Dependabot**（`npm` と `github-actions`）を追加する。悪用されている脆弱性（KEV）は、数日以内に更新する |
| 4 | Node.js を 24 LTS に更新する（20 は 2026-04-30 にサポートが終了した） |
| 5 | `.npmrc` に `min-release-age=7`（npm 11.10 以降）と `ignore-scripts=true` を設定する。install script が必要なパッケージだけ、個別に許可する |
| 6 | GitHub Actions を**コミット SHA に固定**し、リポジトリ設定で SHA 固定を強制する（`pinact` で自動化できる）。CI で使うツール（`wait-on`、`firebase-tools`）もバージョンを固定する |
| 7 | CI の `permissions` を最小にする。全体は `contents: read` にし、`issues: write` は ZAP のジョブだけに付ける |
| 8 | deploy を **push で CI が成功したときだけ**（`workflow_run.event == 'push'`）にし、**CI が検査したコミット**（`head_sha`）をデプロイする |
| 9 | ZAP は対応不要と決めた指摘を rules ファイルで除外し、新しい指摘で CI を失敗させる |

依存パッケージの追加・更新・インストールの詳しい方針は §10.7 に書く。

## 8. 受容したリスク

| リスク | 受容する理由 | 見直す条件 |
|---|---|---|
| T2: PC の感染 | PC の管理は旅館側の運用で、アプリからは手を出せない | PC の管理方法が変わったとき。宿泊業界で同じ手口の被害が増えたとき |
| T3・T4: 開発者ツールで端末 Cookie・セッション Cookie をコピーされる | 意図的な内部犯行で、DBSC がないと防げない | DBSC を導入するとき |
| 認可がない（全アカウントが全機能を使える） | アカウントは PC 単位で、人数も少ない | スタッフごとのアカウントを作るとき。PC 以外から使い始めるとき |
| 人単位の監査ログがない | アカウントが PC 単位なので、人を特定できない | 同上 |
| MFA がない | 端末登録で代わりにする | 端末登録をやめるとき。PC 以外から使い始めるとき |
| 大規模な DDoS | 小規模なアプリで、Cloud Armor などはコストに見合わない。Cloud Run の最大インスタンス数と予算アラートで、請求額だけを抑える | 業務が止まって実害が出たとき |
| npm audit の high（`@grpc/grpc-js`）を例外にしている | このアプリでは実行されないコード（`docs/KnownIssues.md`） | 2027-01-31。またはログインのサーバー経由化（T1-3）が終わったとき（その時点で削除する） |

## 9. 実施計画

| 段階 | 内容 | 効く脅威 | 種類 |
|---|---|---|---|
| P0 | GitHub・Google のパスキー、IAM の確認、WIF の条件、新規登録が API レベルで無効かの確認、予算アラート、§10.1 で P0 とした項目 | T5、T1 | 設定 |
| P1 | Cloud Run の専用サービスアカウントと最大インスタンス数、Slack の Webhook を Secret Manager へ、`firestore.rules`（全拒否）とテスト、SHA 固定、Dependabot、`permissions` の縮小、deploy の修正、`.npmrc`、Node 24、ZAP の rules、ログイン成功時の IP 通知（観察を始める）、§10 で P1 とした項目（検知とアラート、SAST、依存パッケージの管理の仕組み（§10.7）など） | T5、T6、T1 | コードと設定 |
| P2 | 端末登録 | T1、T3、T2（一部）、T4（一部） | コード |
| P3 | ログインのサーバー経由化、失敗回数の制限、パスワードの事前チェック（`firebase` パッケージの削除、API キーの作り直し、CSP と audit 例外の整理） | T1 | コード |
| P4 | パスワードを作り直してから、パスワードポリシー（Require モード）を有効にする | T1 | 設定 |
| P5 | DBSC | T4、T3 の残るリスク | コード |
| P6 | Terraform による設定のコード化と、ずれの自動検知（§10.2）。P1 が終わったあとなら、いつ始めてもよい | T5、T6 | コード |

**順番の理由**

- **P0・P1 を最初に行う**。T5 と T6 は被害が致命的で、多くは設定の変更か小さなコード変更で済む。
- **P2（端末登録）を P3（サーバー経由化）より先に行う**。端末登録は「セッション Cookie を発行する関所」の `/api/auth/login` で確認するので、サーバー経由化しなくても効く（P1 で Firestore を全拒否にしておけば、ID トークンだけでは何もできない）。端末登録は T1・T2・T3・T4 にまとめて効く。サーバー経由化の主な効果は「パスワード試行の回数制限」で、強いパスワードを使っている今は効果が比較的小さい。
- 各段階は AGENTS.md の実装方針（E2E → domain の unit test → …）に沿って進める。設計（端末登録のスキーマ、登録コードの発行方法など）は、着手するときにこの文書か `docs/Security.md` に追記する。

**脅威とは直接結びつかないが実施する改善**

- 予約 API の文字列と配列に、長さの上限を付ける（`src/lib/api/reservationSchemas.ts`）。Firestore の 1 MiB 上限の超過やデータの破損を防ぐ。既存データの最大長を測ってから、まず書き込み側にだけ入れる（読み取り側は上限を超えると空文字に置き換えるため）。

## 10. 脅威への対策を支える仕組み（点検・検知・対応）

§7 の対策は、設定が正しいまま保たれ、異常に気付けて、起きたときに動けることが前提になる。ここではその仕組みを決める。§1 のルールどおり、各項目に効く脅威を書く。

### 10.2 設定のコード化（IaC）

コンソールでの手作業は、変更の記録が残らず、知らないうちに設定がずれる。設定をコードにして、次の効果を得る。

- 設定の変更が PR になり、レビューと履歴（いつ・何を）が残る
- コンソールで誰かが手で変えても、差分として検知できる
- 環境を作り直すときや、staging を作るときに同じ設定を再現できる（`docs/KnownIssues.md` の「staging 環境がない」にも効く）

| 段階 | 対象 | 方法 |
|---|---|---|
| 1（P1 に含まれる） | Firestore Rules、Cloud Run の設定（サービスアカウント、最大インスタンス数、secrets）、Dependabot、npm の設定、ZAP の除外ルール | リポジトリ内のファイル（`firestore.rules`、`deploy.yml` の flags、`.github/dependabot.yml`、`.npmrc`、ZAP の rules ファイル） |
| 2（P6） | GCP と Firebase（§10.1 の F・G、§7 の WIF・IAM・サービスアカウント、§10.3 のアラート、予算） | Terraform。既存のリソースは `import` ブロックで取り込む（作り直さない）。state はバージョニングを有効にした GCS バケットに置く |
| 3（任意） | GitHub の設定（ルールセット、Environment、Actions の権限など） | Terraform の `integrations/github` provider。項目が少ないので、四半期ごとの手作業の点検で済ませてもよい |

- **ずれの自動検知**: GitHub Actions で週1回、読み取り専用のサービスアカウントで `terraform plan -detailed-exitcode` を実行し、差分があれば通知する。
- Identity Platform の一部の項目（新規登録の無効化、メール列挙保護、リクエストログ）を Terraform provider がどこまで扱えるかは要確認。
- **コード化できないもの**: アカウント自体の 2FA / パスキー、Terraform の state バケットと Terraform 用アカウントの最初の作成、F2・G5 の「中身」の確認。
- CI/CD を変更するときは、AGENTS.md のとおり `docs/CICD.md` も同時に更新する。

### 10.3 検知とアラート

対策をすり抜けた攻撃や、設定の誤りに気付くための仕組み。通知が Slack だけだと、Slack の障害や Webhook の失敗に気付けないので、**重大なものはメールにも送る**。

| 検知すること | 方法 | 効く脅威 | 段階 |
|---|---|---|---|
| ログイン成功時の接続元 IP | `/api/auth/login` で Slack に通知する（T1 の対策1） | T1、T2、T3 | P1 |
| Google 側でのログイン失敗 | F5 のログに、Cloud Logging のログベースのアラートを付ける。P3 以降は、自前のログと通知に置き換える | T1 | P1 |
| 5xx・想定外のエラーの急増 | ログベースのアラート | T6 | P1 |
| Slack 通知の失敗（今はログに出るだけで気付けない。`docs/KnownIssues.md`） | `Slack通知失敗` のログに、ログベースのアラートを付け、メールで通知する | 全般 | P1 |
| GCP の管理操作（IAM の変更、サービスアカウントの鍵の作成、Cloud Run の設定変更） | Cloud Audit Logs（管理アクティビティのログは既定で有効）にアラートを付ける | T5 | P1 |
| 予算の超過 | 予算アラート（メール） | §8 の DDoS | P0 |
| 依存パッケージの脆弱性、シークレットの漏えい | Dependabot と Secret scanning の通知をメールで受け取る | T5、T6 | P1 |

### 10.4 インシデント対応の手順

起きたときに迷わないよう、最初にやることを決めておく。

| 起きたこと | すぐやること |
|---|---|
| PC の紛失・盗難 | Firebase コンソールで、その PC のアカウントを無効にする（次の API 呼び出しから 401 になる）。端末登録を入れたあとは、その端末の登録も削除する。パスワードを作り直してから、アカウントを有効に戻す |
| パスワード漏えいの疑い（知らない IP からのログインの通知など） | 上と同じ。加えて、そのセッションで行われた操作をログで確認する |
| Slack の Webhook URL の漏えい | Slack で Webhook を作り直し、Secret Manager の値を更新する |
| 管理者アカウントの乗っ取りの疑い | パスワードとパスキーを再設定し、全セッションを無効にする。IAM、Cloud Audit Logs、GitHub の audit log で変更を確認する。WIF とデプロイを止め、直近にデプロイされたイメージを確認する |
| 悪性パッケージを入れた疑い（axios の事例のようなもの） | lock ファイルと、デプロイごとの SBOM（§10.7）で、該当バージョンが入っていたか・いつ本番に出たかを確認する。開発 PC と CI の認証情報（GitHub のトークン、gcloud、npm）をすべて作り直す。該当パッケージを安全なバージョンに戻す |
| 個人情報の漏えい、またはそのおそれ | 不正アクセスによる漏えい（おそれを含む）は、件数にかかわらず個人情報保護委員会への報告と本人への通知が必要。速報は速やかに（目安3〜5日）、確報は30日以内（不正の目的によるものは60日以内）。宿泊客へ偽メッセージへの注意を呼びかける。必要なら Firestore の PITR で復元する（期限と手続きは、個人情報保護委員会の最新の手引きで要確認） |

### 10.5 検査と継続的な点検

| 項目 | 内容 | 効く脅威 | 段階 |
|---|---|---|---|
| SAST | Semgrep を CI に追加する（CodeQL は、private リポジトリだと有料になる場合がある） | T6 | P1 |
| ZAP の full scan | CI の中で起動したサーバーに対して実行する（本番には実行しない）。`docs/KnownIssues.md` の「full モードを試していない」への対応。ログイン後の画面の検査は、端末登録のあとに検討する | T6 | P1 |
| ASVS 5.0 L1 の棚卸し | 年1回、この文書と実装を ASVS L1 の項目と突き合わせる | 全般 | 継続 |
| エラーで出す情報 | 400 のレスポンスに Zod の詳細（`details: parsed.error.flatten()`）を返している。入力の構造が外から分かるので、本番では返さないか、受容するかを決める | T1 | P1 |
| KnownIssues の古い記述 | 「CI が通らなくても deploy される」は、`deploy.yml` の `conclusion == 'success'` で解消済みの可能性がある。確認して更新する | — | P1 |

### 10.6 検討して採用しなかった・保留した対策

| 対策 | 判断 | 理由 | 見直す条件 |
|---|---|---|---|
| ログアウトボタン | 採用しない | スタッフ専用の PC で使う。緊急時はアカウントを無効にすれば、セッションも失効する（§10.4） | 不特定の人が触れる場所に PC を置くとき |
| IAP（Google アカウントによる前段の認証） | 保留 | Edge でも使う。スタッフ用の Google アカウントの運用が必要になる | 端末登録が運用に合わないとき。スタッフごとのアカウントを作るとき |
| 異常時のアカウント自動無効化 | 保留 | 端末登録で未登録の端末を拒否できるので、追加の効果が小さい | 端末登録のあとも、不審なログインが観察されたとき |
| Trusted Types | 保留 | React が自動でエスケープし、`dangerouslySetInnerHTML` も使っていないので効果が小さい。Next.js / MUI / Firebase が動かなくなるおそれがある | HTML を直接扱う機能を追加するとき。試すときは Report-Only から始める |
| HSTS preload | 不要 | `*.run.app` は `.app` ドメインごと preload 済み | 独自ドメインに移るとき |
| MFA | 不要（§8） | 端末登録で代わりにする | §8 のとおり |

### 10.7 依存パッケージの管理

依存パッケージは、T6（悪性パッケージ、既知の脆弱性）の入口（E6）である。このアプリのコードより依存のコードのほうがはるかに多いので、**数を増やさない・入れるときに確かめる・入れ方を固める・すぐ更新できる**の4つで管理する。

#### 現状（2026-11-01 時点）

| 項目 | 状態 |
|---|---|
| パッケージの数（lock ファイル上） | 808（本番用 367、開発用 441）。直接の依存は本番用 15、開発用 14 |
| 署名と provenance | `npm audit signatures` で、714 パッケージのレジストリ署名と、149 パッケージの attestation（provenance）を確認できた |
| install script を持つもの | `@firebase/util`（ブラウザ用 `firebase` から。Firebase Hosting 用の既定設定を書き出す処理で、このアプリでは不要）、`protobufjs`（`firebase-admin` から。バージョン表記の警告を出すだけ）、`esbuild`・`unrs-resolver`（開発用。バイナリの取得や確認）、`fsevents`（開発用、macOS のみ） |
| 既知の脆弱性の例外 | `@grpc/grpc-js` の high（§8、`scripts/ci/auditAllowlist.ts`）。`firebase-admin` 経由の low 8件（`docs/KnownIssues.md`） |
| バージョンのずれ | `@types/node` が `^20`（Node 24 への更新時に合わせる）。`eslint-config-next` が 16.2.1 で、`next`（16.4.3）とずれている |
| 自動更新 | なし（Dependabot が未設定） |

#### 追加するときの基準

新しい依存を入れる PR には、次を確認した結果を書く。

| 確認すること | 基準 |
|---|---|
| 本当に必要か | 標準 API（Web API、Node.js）や、すでに入っている依存で代わりにできないか。数十行で書ける小さな処理なら自分で書く。ただし暗号・認証・入力のパースなど、間違えると危険なものは自作しない（§2） |
| メンテナンスの状態 | 最近もリリースがあるか。メンテナが1人だけではないか。利用者が十分に多いか |
| 発行元の確かさ | provenance（attestation）付きで公開されているか |
| install script | あるなら、何をするかを読む。不要なら `ignore-scripts` のまま使えるか確かめる |
| 連れてくる依存の数 | lock ファイルの差分で、増えるパッケージの数を確認する |
| 置き場所 | テストやビルドにしか使わないものは `devDependencies` に入れる（本番のイメージに入れない） |
| ライセンス | 商用利用できるもの（MIT、Apache-2.0、BSD など） |

#### 更新の方針

| 種類 | 方針 |
|---|---|
| 実際に悪用されている脆弱性（KEV に載っている、React2Shell のように悪用が報告されている）で、このアプリで実行されるもの | **数日以内**に更新してデプロイする |
| high / critical で、このアプリで実行されるもの | 1〜2週間以内に更新する |
| 実行されないもの | 例外リストに理由と期限を書いて許可する（今の `auditAllowlist.ts` の運用） |
| 通常の更新（minor / patch） | Dependabot で週1回、まとめて PR にする（`groups`）。公開から7日たったものだけを対象にする（`cooldown`。セキュリティ更新には適用されないので、修正は遅れない） |
| major の更新 | 1パッケージずつ別の PR にする。Context7 で移行ガイドを確認する（AGENTS.md） |
| React / Next.js | 公式のセキュリティ情報（Next.js の GitHub advisories、React のブログ）を見る。RSC と proxy は、繰り返し脆弱性が出ている場所 |

更新の PR では、CI が通ることに加えて **lock ファイルの差分**を見る。知らないパッケージが増えていないか、install script を持つものが増えていないか、`resolved` が `registry.npmjs.org` 以外を指していないかを確認する。

#### インストールの防御

| 対策 | 内容 |
|---|---|
| lock ファイルどおりに入れる | CI と Docker では `npm ci` だけを使う（今もそうなっている）。`npm install` は依存を変えるときだけ使う |
| `.npmrc` をリポジトリに置く | `ignore-scripts=true` と `min-release-age=7`。npm 11.10 以降が必要（Node 24 への更新とあわせて npm も更新する） |
| `ignore-scripts` の確認 | 導入前に `npm ci --ignore-scripts` のあと、lint、型チェック、unit、emulator、E2E、build がすべて通ることを確かめる。上の install script は、このアプリでは不要か代わりの仕組みがある見込みだが、実際に確認する |
| Docker build | 今の Dockerfile は、依存を入れる段階で `package.json` と `package-lock.json` しかコピーしていない。**`.npmrc` もコピーしないと、イメージのビルドでは設定が効かない** |
| 署名の検証 | CI に `npm audit signatures` を追加する。署名が不正なパッケージがあれば失敗させる |
| 開発 PC | リポジトリの `.npmrc` は、このリポジトリの中だけで効く。ほかのプロジェクトも含めて守るなら、`~/.npmrc` にも同じ設定を書く。バージョンを指定しない `npx <パッケージ>` は使わない |

#### 実行環境とベースイメージ

- Node.js は 24 LTS にする（Dockerfile、CI、`@types/node`）。
- Docker のベースイメージ（`node:24-alpine`）は digest で固定し、Dependabot（`docker`）で更新する。
- 本番のイメージには `standalone` の出力だけを入れる（今もそうなっている。開発用の依存はイメージに入らない）。

#### GitHub Actions

- アクションも依存の一つとして扱う。コミット SHA に固定し（T6）、Dependabot（`github-actions`）で更新する。
- できるだけ GitHub や Google などの公式のアクションを使う。サードパーティのアクション（今は `zaproxy/action-baseline`）は、更新の PR で差分を見てから取り込む。

#### SBOM（部品表）

- デプロイのたびに、`npm sbom --sbom-format cyclonedx` で SBOM を作り、GitHub Actions の artifact として残す。
- 「乗っ取られたバージョンが本番に入っていたか」に、すぐ答えられるようにするため（§10.4）。

#### 減らす候補

| 依存 | 方針 |
|---|---|
| `firebase`（ブラウザ用） | ログインのサーバー経由化（P3）で削除する。`@grpc/grpc-js` の例外と、`@firebase/util` の install script もなくなる |
| `eslint-config-next` | `next` とバージョンを合わせる |
| そのほか | 四半期の点検（§10.1）のときに、使っていない依存がないか確認する |

## 11. 見直し

次のときに、この文書を見直す。
- 四半期に1回（§10.1 の点検と同時に行う）
- §8 の見直し条件に当てはまったとき
- 新しい入口ができたとき（外部 API、スタッフ別のアカウント、公開ページ、新しい外部サービス）
- 宿泊業界や依存パッケージで、重大なインシデントが起きたとき

「十分か」は、各脅威の「残るリスク」と §8 を読み、受容できるかで判断する。
