# Security Policy（脅威モデルと対策方針）

## 2. 判断の原則

- **リスク ＝ 起こりやすさ × 被害**。両方を見て順番を決める。
- 脆弱性は深刻度スコア（CVSS）だけで判断しない。「実際に悪用されているか（CISA KEV など）」と「このアプリで実行されうるコードか」で判断する。
- 脅威モデリングを用いる
- リスクへの対応は「低減・回避・移転・受容」の4択。受容したリスクは、理由と見直す条件を §8 に書く。

## 3. 前提（運用の実態）

- 利用する PC は約4台、スタッフは約10名。Firebase Auth のアカウントは **PC 単位**（人単位ではない）。
- 新規登録は無効。認可（ロール）は持たず、ログインできれば全機能を使える。
- ログインは Chrome / Edge のパスワードマネージャーの自動入力。パスワードは openssl で生成した。パスワードの変更機能はない。
- 本番は Cloud Run の `*.run.app` で、`.app` ドメインは全体が HTTPS強制する。利用できる時間は 6:00〜23:00 JST。
- PC の管理（OS、ブラウザ、メール）は旅館側の運用で、このアプリからは手を出せない。
- リポジトリは非公開。開発にはCloud codeを使う。

## 4. 守るもの

| 資産 | 場所 | 漏えい・改ざん・停止したときの被害 |
|---|---|---|
| 宿泊客の個人情報（氏名、国、メール本文のメモなど） | Firestore `guestInfoV2` | 宿泊客を狙う詐欺の材料になる。旅館の信用を失う。個人情報保護法にもとづく報告が必要になる(圧倒的最重要) |
| 宿泊税・金庫残高の記録 | `guestInfoV2`、`dailyInfo` | 改ざんされると会計が合わなくなる |
| 当日の業務（タイムテーブル、清掃ボード） | アプリ全体 | 止まると、当日の段取りに支障が出る |
| 本番環境の管理権限 | GitHub、GCP、Firebase | アプリの認証を通らずに全データを読まれる。改ざんしたコードをデプロイされる(重要) |

## 5. 入口（攻撃面）

```
[旅館の PC 4台] ──HTTPS──> [Cloud Run *.run.app（公開）] ──Admin SDK──> [Firestore]
      │
      └─(現状) パスワード ──> [Identity Toolkit（公開 API キーで誰でも呼べる）]

[開発 PC + AI エージェント] ──> [GitHub] ──CI / WIF──> [Artifact Registry] ──> [Cloud Run]
[npm レジストリ / GitHub Actions] ──> 開発 PC・CI・Docker build
```

| # | 入口 | 誰が到達できるか |
|---|---|---|
| E1 | Cloud Run の公開 URL | インターネット上の誰でも |
| E2 | Identity Toolkit（パスワードの判定） | API キーがブラウザ用のバンドルに入っているので、誰でも直接呼べる |
| E3 | Firestore | ブラウザからは使っていないが、Security Rules 次第では ID トークンで直接読める |
| E4 | 旅館の PC | スタッフ、ゲスト、PC に感染したマルウェア。保存されたパスワードと Cookie がある |
| E5 | GitHub・GCP・Firebase の管理者アカウント | アカウントを乗っ取った人 |
| E6 | 依存パッケージ、GitHub Actions | パッケージやアクションのメンテナ（乗っ取られた場合を含む） |
| E7 | Git リポジトリ（過去の履歴を含む） | リポジトリを読める人。GitHub アカウントを乗っ取った人。公開に切り替えた場合は誰でも |

## 6. 想定する攻撃者

| 型 | 実態 | 目的 |
|---|---|---|
| 無差別型のボット | 公開したサーバーは、すぐに自動スキャンを受ける。既知の脆弱性（React2Shell など）は、公表から間もなく大量に悪用される | 踏み台、暗号資産の採掘、データの窃取 |
| 宿泊業界を狙う犯罪グループ | Booking.com を装ったメールで偽の確認画面に誘導し、スタッフ自身にコマンドを実行させて（ClickFix）、情報を盗むマルウェアを入れる（Storm-1865、2024年12月〜）。予約管理システムへの不正アクセスのあと、予約者に偽のメッセージが送られた事例もある（TEMAIRAZU、2026年9月。最大約445万人が対象になる可能性。両者の関係は調査中と発表） | 予約データを使った、宿泊客への詐欺 |
| サプライチェーン攻撃者 | npm のメンテナのアカウントを乗っ取り、悪性のバージョンを公開する（axios、2026年3月。Shai-Hulud） | 開発 PC と CI の認証情報 |
| 内部の人 | スタッフ（退職者を含む）やゲストが、旅館の PC に触れられる | パスワードを持ち帰り、外から使う |

**有名旅館であること**は、宿泊客が詐欺の標的として価値が高いことを意味する。

想定しない攻撃者:
- 国家レベルの攻撃者（ゼロデイ脆弱性、ハードウェアへの攻撃）
- 大規模な DDoS（§8 で受容する）
- 盗んだ PC を解析すること（PC を紛失・盗難したら、その端末とアカウントを無効にして対応する）

## 7. 脅威と方針

| # | 脅威 | 入口 | 起こりやすさ | 被害 | 方針 |
|---|---|---|---|---|---|
| T1 | ボットによる総当たり | E1、E2 | 高（常に来る） | 中（パスワードが強いので成功しにくい） | 低減 |
| T2 | ClickFix などで PC が感染し、パスワードや Cookie を盗まれる | E4 | 中 | 大 | 受容（一部を低減） |
| T3 | パスワードの盗み見・持ち出し | E4 | 中 | 大 | 受容（端末登録で低減） |
| T4 | Session Cookie のコピー | E4 | 低〜中 | 大 | 低減 |
| T5 | 開発者・管理者アカウントの乗っ取り | E5 | 低〜中 | 致命的 | 低減（最優先） |
| T6 | 既知の脆弱性・悪性パッケージの悪用 | E1、E6 | 高 | 致命的 | 低減（最優先） |
| T7 | ソースコードの欠陥（AI が生成したコードを含む） | E1 | 中〜高 | 大 | 低減 |
| T8 | 機密情報・宿泊客の実データの混入 | E7 | 低〜中 | 大 | 低減 |

具体的な対策は `docs/SecurityMeasures.md` の §2 に、脅威の番号ごとに書く。

### T1: ボットによる総当たり

**説明**: インターネットに公開されたログイン画面に、ボットがパスワードを大量に試す。今の構成では、パスワードの判定がブラウザから Google の Identity Toolkit に直接送られ、そのための API キーも公開されている（E2）。そのため攻撃者は**アプリを通らずに Google の窓口へ直接総当たりでき**、アプリ側に回数制限を作っても回り込まれる。一方で、パスワードは openssl で生成しているので、推測で当てることは現実的にできない。

**方針: 低減**
- パスワードを試す**裏口（E2）をなくす**。パスワードの試行は、すべてアプリのサーバーを通るようにする。
- 登録した PC 以外からは、**パスワードの判定まで到達させない**。
- 試行を**観察できる**ようにし、外からのログインに気付けるようにする。
- 特定の回数以上間違えたらx分後まで使えないみたいにしたい。

**残るリスク**: 登録済みの PC を使われる場合（T2、T3）。

### T2: ClickFix などで PC が感染し、パスワードや Cookie を盗まれる

**説明**: 犯罪グループが Booking.com を装ったメール（悪い口コミが付いた、予約の問い合わせ、など）で偽の CAPTCHA 画面に誘導し、「確認のため」と称してスタッフ自身にコマンドを貼り付けて実行させる。そうして PC にマルウェアを入れ、保存されたパスワードや Cookie を盗む。盗んだ予約データは、宿泊客への詐欺メッセージに使われる。

**方針: 受容する**（PC の管理は旅館側の運用で、アプリからは手を出せない）
- ただし、T1・T3・T4 の対策で「盗んだものを**外から使えない**」ようにして、被害を小さくする。

### T3: パスワードの盗み見・持ち出し

**説明**: スタッフやゲストが旅館の PC のブラウザを使い、保存されたパスワードを盗み見る。自動入力させてから開発者ツールで `type="text"` に書き換えれば、OS の認証なしでも平文が見える。盗んだパスワードは、自宅からでも退職後でも外から使える。

**方針: 受容する**（ブラウザの設定はアプリからは変えられない）
- ただし、**パスワードだけでは登録した PC 以外から使えない**ようにして、ほぼ防ぐ。

**残るリスク**: 開発者ツールで端末の証明（Cookie）まで意図的にコピーされる場合（T4 で扱う）。

### T4: Session Cookie のコピー

**説明**: ログイン中の PC で開発者ツールを開くと、`session` Cookie が見える（`httpOnly` は JavaScript からの読み取りを防ぐだけ）。これをコピーすれば、別の PC でも 23:00 までログインした状態で使える。今の Cookie は「持っている人なら誰でも使える入館証」になっている。

**方針: 低減**
- セッションの寿命を短く保つ（今は当日 23:00 で切れる）。
- 将来は、Cookie を **PC のハードウェアに結び付け**、コピーしても他の PC では使えないようにする。

**残るリスク**: 感染した PC の上で、その場で悪用されること。

### T5: 開発者・管理者アカウントの乗っ取り

**説明**: GitHub・GCP・Firebase のアカウントを乗っ取られると、**アプリの認証を通らずに** Firestore の全データを読まれたり、改ざんしたコードを本番にデプロイされたりする。アプリ側の対策では防げない、別の入口（E5）である。開発 PC でマルウェア（T6）や AI エージェントの誤操作が起きた場合も、ここに行き着く。

**方針: 低減（最優先）**
- 管理者アカウントは、**フィッシングに強い認証**（パスキー）で守る。
- 本番を操作できる人とサービスアカウントを**最小限**にし、CI から本番への経路も、このリポジトリの main だけに限る。
- 乗っ取られても復元できるように、データのバックアップを持つ。

### T6: 既知の脆弱性・悪性パッケージの悪用

**説明**:
- **フレームワークの脆弱性**: React2Shell（CVE-2025-55182、RSC のデシリアライズによる RCE）は、公表直後から大量に悪用された。Next.js でも 2026 年に、middleware / proxy の認証をすり抜ける脆弱性が何度も出た（このアプリは proxy を認証の境界にしていないので、影響を受けにくい）。
- **悪性パッケージ**: 乗っ取られたバージョンの postinstall スクリプトは、開発 PC・CI・Docker build の `npm ci` で実行される。
- **被害が広がる経路**: Cloud Run で RCE を起こされると、そのサービスアカウントの権限で GCP を操作される。既定の Compute Engine サービスアカウントにはプロジェクト全体の Editor が付いていることがあり、その場合は全データと全リソースが対象になる。

**方針: 低減（最優先）**
- **すぐ更新できる**状態を保つ（§10）。
- 悪性のコードが**入りにくく、入っても実行されにくい**インストールにする。
- 侵入されても**被害の範囲を小さく**する（最小権限、Firestore への直接アクセスの禁止）。

### T7: ソースコードの欠陥（AI が生成したコードを含む）

**説明**: 自分、または AI のコーディング支援が書いたコードに脆弱性が入る。このアプリで特に起こりやすく、被害が大きいのは次の3つ。
- 新しい API で、session の確認（`requireSession`）を忘れる（A01）
- 入力の長さや件数に上限がない
- エラーのレスポンスやログ、Slack に内部の情報や個人情報を出す

**方針: 低減**
- 人の注意に頼らず、**機械で止める**（テスト、静的解析）。機械で見つけられない設計上の欠陥は、この文書の脅威の整理とレビューで見る。

### T8: 機密情報・宿泊客の実データの混入

**説明**: API キーや Webhook の URL、**宿泊客の実データ**を Git に入れて push してしまう。一度 push すると履歴に残り続け、リポジトリを読める人全員に見える。今は本物の秘密情報をほとんど持っていない（GCP は WIF で鍵ファイルがなく、開発環境は Emulator だけ）が、ログインのサーバー経由化（T1）でサーバー専用の API キーが増える。また、秘密情報の検査ツールでは**個人情報は見つけられない**。

**方針: 低減**
- **秘密情報そのものを持たない**ことを第一にする。持つものは、シークレット管理（Secret Manager、GitHub Secrets）にだけ置く。
- 実データは**開発の場に持ち込まない**。テストデータは匿名化・生成したものだけを使う。
- 漏れたら、**履歴から消すより先にキーを無効化する**。
- リポジトリを公開する前に、全履歴を検査する。

## 8. 受容したリスク

| リスク | 受容する理由 | 見直す条件 |
|---|---|---|
| T2: PC の感染 | PC の管理は旅館側の運用で、アプリからは手を出せない | PC の管理方法が変わったとき。宿泊業界で同じ手口の被害が増えたとき |
| T3・T4: 開発者ツールで端末の Cookie・セッション Cookie をコピーされる | 意図的な内部犯行で、Cookie をハードウェアに結び付けないと防げない | Cookie をハードウェアに結び付ける対策（DBSC）を導入するとき |
| 認可がない（全アカウントが全機能を使える） | アカウントは PC 単位で、人数も少ない | スタッフごとのアカウントを作るとき。PC 以外から使い始めるとき |
| 人単位の監査ログがない | アカウントが PC 単位なので、人を特定できない | 同上 |
| MFA がない | 端末登録で代わりにする | 端末登録をやめるとき。PC 以外から使い始めるとき |
| 大規模な DDoS | 小規模なアプリで、Cloud Armor などはコストに見合わない。請求額だけを抑える | 業務が止まって実害が出たとき |
| npm audit の high（`@grpc/grpc-js`）を例外にしている | このアプリでは実行されないコード（`docs/KnownIssues.md`） | 2027-01-31。またはログインのサーバー経由化が終わったとき（その時点で削除する） |
